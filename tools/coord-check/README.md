# 坐标转换交叉验证（开发期工具）

`coordtransform_dart` 与百度官方 `geoconv/v2` 的逐点比对。**不属于 Flutter 客户端代码**，
服务端 AK/SK 只在本机开发期使用，不得移入 `app/`，不得打包进 APK。

引入这个包之前必须跑一次：它把 ADR 0001 D3 的起点转换从「需要 AK 的网络接口」降级为
纯本地计算，算错就会让老人从错误的起点开始导航。包自己的测试断言不能当证据。

## 跑法

```bash
# Flutter SDK 的 bin 要在 PATH 里（脚本要调 dart）
export PATH=<flutter>/bin:$PATH        # Windows Git Bash 同样写法，路径用 /c/... 形式
cd tools/coord-check && dart pub get && cd ../..
set -a && . ./.env.local && set +a
python3 tools/coord-check/crosscheck.py   # Windows 上命令名可能是 python
```

Windows 用 **Git Bash** 跑（`set -a` / `. ./.env.local` 是 bash 语法，cmd 与 PowerShell 不认）。
脚本用 `shutil.which` 解析 `dart`，因此 Windows 上的 `dart.bat` 也能找到。

退出码 0 = 通过（最大偏差 ≤ 1 米），1 = 不通过。产物 `points.json` / `dart_out.json`
已在 `.gitignore` 里，不入库。

## 并发纪律：全程串行，并发恒为 1

个人认证的服务端 AK，**路线规划服务只有 3 并发**，且客户端超时不释放服务端槽位
（ADR 0002 §2.2 / A8）。坐标转换服务的上限未确认，所以这个脚本不赌，直接串行：

- `conv()` 是阻塞 `for` 循环，**一次只有一个在途请求**，没有线程池、没有 `asyncio`；
- **批量不是并发**：一个请求最多带 `CHUNK = 10` 组坐标，只占 1 个槽。17 个点拆成 2 个请求，
  而不是 17 个并发请求；
- 一次完整运行共 **11 个** `/geoconv/v2/` 请求：反解迭代 4 + 收敛校验 1 + bd09→gcj02 1
  + model=2 两批 2 + model=1 1 + 归因 model=5 两批 2；
- 任何 `status != 0` 直接 `sys.exit`，**不重试**——卡住的请求加重试才是耗尽槽位的典型路径。

改动这个脚本时不要为了「跑快点」把 `conv()` 并行化。省下的几秒换来的是配额告警和
可能被封的 AK，而这个脚本一共只跑几次。

## 为什么要有「数值反解」这一步

`geoconv/v2` 只支持 **model 1–6**，没有 `bd09ll → wgs84`（model 7 及以上返回
`status=29 param error:model illegal`）。而仓库里的公共地标锚点全是 `bd09ll`
（fixture 用 `coord_type=bd09ll` 录制）。为了拿到这些地标真正的 WGS84 输入，
脚本用官方 `model=2` 做不动点迭代反解：`W ← W + (A − model2(W))`，迭代 4 次。

实测的 model 语义（2026-11-12，用合肥南站-地铁站锚点逐个试出来）：

| model | 含义 | 证据 |
|---|---|---|
| 1 | gcj02ll → bd09ll | 与 model=5 互逆，往返偏差 **0.090 m** |
| 2 | wgs84 → bd09ll | 偏移量级 ≈1.2 km，符合 wgs84→bd09 总偏移 |
| 3 | bd09ll → bd09mc | 返回墨卡托米（13057594.96, 3714992.98） |
| 4 | bd09mc → bd09ll | 对 ll 输入返回接近 0 的垃圾值 |
| 5 | bd09ll → gcj02ll | 与 model=1 互逆 |
| 6 | 与 model=4 同输出 | 未进一步区分，本项目不用 |
| ≥7 | 不支持 | `status=29` |

## 测点

- **5 个公共地标锚点**：合肥南站-地铁站、合肥火车站、大蜀山森林公园、安徽省立医院、
  合肥南站。坐标取自 `app/test/fixtures/*_walking.json`，脚本启动时会校验锚点确实
  出现在 fixture 里，防止手抄抄错。全是公共场所，符合 `GIT_COMMIT_RULES` §3.1。
- **10 个算法扫描点**：北京/上海/广州/成都/哈尔滨/乌鲁木齐/拉萨/三亚/喀什/漠河。
  作用是把比对范围从合肥扩到全国，并覆盖国境矩形的边界附近。
  这些点只要求「同一批数字喂给两个实现」，不要求坐标本身权威。
- **2 个境外点**：东京、伦敦。不参与 1 米判定，只记录两边各自的行为。

## 2026-11-12 实测结果

| 比对项 | 点数 | 最大偏差 |
|---|---|---|
| 官方 model=2 反解的往返精度 | 5 | 0.023 m |
| `gcj02ToBd09` vs 官方 model=1 | 5 | **0.0001 m** |
| `wgs84ToBd09` vs 官方 model=2 | 15 | **0.7135 m** |
| `wgs84ToGcj02` vs 官方 model=2→model=5 | 15 | 0.7656 m |

**判定：通过。** 偏差归因清楚：`gcj02 → bd09` 半段与官方逐点一致到 0.1 毫米，
亚米级偏差全部来自 `wgs84 → gcj02` 半段——公开的闭式算法是对官方未公开修正量的近似，
这是该算法的固有精度，不是这个包的实现缺陷。0.7 米远小于手机 GPS 的 5–20 米精度，
也小于百度 POI 本身的定位误差，对「步行到上车站」这种米级文案无影响。

**境外行为一致但都静默**：东京与伦敦两个点，包与官方 model=2 **都原样返回输入坐标**
（偏差 0.0000 m，包的 `passthrough=True`）。也就是说境外不会报错，而是把 WGS84 当 BD-09 用。
V1 只在境内使用，若将来支持境外必须显式拦截，不能依赖转换函数报错。

## 结论的边界

- 只验证了**正向** `wgs84 → bd09`。反向 `bd09ToWgs84` / `gcj02ToWgs84` 未验证，
  且调研已指出 `gcj02ToWgs84Raw` 用的是粗糙的 `lng*2-out[0]` 近似——**不要用反向函数**。
- 没有真机 GPS 实测。0.7 米是与官方接口的算法偏差，不是端到端定位误差。
- 包未加入 `app/pubspec.yaml`：D3 的转换代码属 M1 定位功能，等写那段代码时再引入，
  避免现在挂一个用不到的依赖。
