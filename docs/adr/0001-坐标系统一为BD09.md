# ADR 0001：坐标系统一为 BD-09，导航终点存 navi_location

**状态**：已接受（2026-11-12）；D3 于 2026-11-12 按交叉验证结果修订
**关联**：方案 §5.1 `coordSystem` 字段、§6.2 验收第 7 条「坐标系无偏移」、评审意见 P0-3、`docs/research/开源项目复用调研.md` §7.1、`tools/coord-check/README.md`
**范围**：仅 M0 核验结论。真机行为仍待验证，见文末。

---

## 背景

评审意见 P0-3 指出坐标混用没有解决方案：终点来自百度 POI（BD-09），起点可能来自手机 GPS（WGS84），一次 URI 调用只有一个 `coord_type`，混用会偏移数百米，足以让老人走错路口。要定方案，先得确认百度到底返回什么坐标系。

## 核验到的事实

以下均为本次实际调用结果，不是文档推断。

1. **`/place/v3/detail` 的 `ret_coordtype` 被静默忽略。** 分别传 `bd09ll`、`gcj02`、`wgs84`，三次响应坐标逐字节相同。因此这个参数既不能用来确认坐标系，也不能用来转换。

2. **`/geoconv/v1/?from=&to=` 是遗留端点，返回无意义结果。** 用它做 bd09→gcj02 得到 Δlng **+0.0119**，而该纬度处理论值约 **−0.006**，符号都是错的。按 v1 写法调用的任何转换都不可信。

3. **现行接口是 `/geoconv/v2/?model=`**，model 取值固定为：1 高德/腾讯→bd09ll，2 GPS→bd09ll，3 bd09ll→bd09mc，4 bd09mc→bd09ll，5 bd09ll→高德/腾讯，6 文档标称 bd09mc→高德/腾讯（用 bd09ll 锚点实测与 model=4 同输出，本项目不用）。**model=5 就是 bd09ll→gcj02 的反向转换**，早期文档里"不存在 bd09ll→gcj02"的说法是错的；真正**不存在的是 bd09ll→wgs84**（model 7 及以上返回 `status=29 param error:model illegal`），因此 GPS 坐标只能正向转成 BD-09，不能把百度坐标转回 GPS。model=1 与 model=5 已实测互逆：同一公共地标往返偏差 **0.090 米**。

4. **Place API 返回的确实是 BD-09。** 用 model=5（bd09ll→高德/腾讯，即 GCJ02）转换家的坐标，得 Δlng **−0.00642**、Δlat **−0.00624**，与该纬度 BD09→GCJ02 理论偏移的符号和量级一致。交叉验证：该坐标取两位小数后与百度网页版免登录选点器（BD-09 原生）显示的值一致；若它本是 GCJ02，取整后百位会差 1。

5. **同一 POI 有两个坐标，差几十米。** `/place/v3/detail` 同时返回 `location`（几何中心）和 `detail_info.navi_location`（导航终点）。家中两者相距约 **58 米**（与 `children[].distance` 字段吻合，该字段就是子点到几何中心的距离）；而 `navi_location` 与 `pv_rate` 标注「93%选择」的主要出入口仅相距约 **3 米**。

6. **手写坐标换算不可靠。** 本次曾自行实现 BD09MC→BD09LL 墨卡托反算，得到纬度 `−9.68e33`。已放弃所有**手写**换算。这不等于放弃本地换算：事实 7 的 `coordtransform_dart` 是逐点对过官方接口的现成实现，D3 采用它。

7. **`coordtransform_dart` 1.0.4 的正向转换已与官方接口逐点交叉验证（2026-11-12）。** 工具与完整数据见 `tools/coord-check/README.md`。5 个公共地标锚点（合肥南站-地铁站、合肥火车站、大蜀山森林公园、安徽省立医院、合肥南站，坐标取自 `app/test/fixtures/`）+ 10 个全国算法扫描点：

   | 比对项 | 点数 | 最大偏差 |
   |---|---|---|
   | `gcj02ToBd09` vs 官方 model=1 | 5 | **0.0001 m** |
   | `wgs84ToBd09` vs 官方 model=2 | 15 | **0.7135 m** |
   | `wgs84ToGcj02` vs 官方 model=2→model=5 | 15 | 0.7656 m |

   偏差归因清楚：`gcj02→bd09` 半段与官方一致到 0.1 毫米，亚米级偏差全部来自 `wgs84→gcj02` 半段——公开闭式算法是对官方未公开修正量的近似，属该算法固有精度，不是包的实现缺陷。0.7 米远小于手机 GPS 的 5–20 米精度。**这不推翻事实 6**：放弃的是自己手写换算，采用的是已对官方基准验证过的实现。

## 决策

- **D1　全链路统一 BD-09。** 地点数据存 BD-09，`coordSystem` 固定写 `bd09ll`，所有 URI 调起传 `coord_type=bd09ll`。不采用评审意见中的方案 B（统一到 wgs84）——由事实 3，百度不提供 bd09ll→wgs84 转换，方案 B 无法用官方接口实现。

- **D2　导航终点存 `navi_location`，不存 `location`。** `location` 只用于地图展示。POI 有出入口子点时，额外记录 `pv_rate` 最高的那个门（含其 uid），因为文档说明带 `destination_uid` 时百度会以出入口作为结束导航位置。方案 §5.1 的地点模型需相应增加 `naviLatitude`/`naviLongitude` 与门的 uid 字段。

- **D3　起点若来自 GPS，用 `coordtransform_dart` 的 `wgs84ToBd09` 本地转 BD-09**（事实 7 已交叉验证，最大偏差 0.71 米）。官方 `/geoconv/v2/?model=2` 保留为校验基准，不进客户端运行时链路。**只用正向函数**：`bd09ToWgs84` / `gcj02ToWgs84` 未验证，且调研指出 `gcj02ToWgs84Raw` 用的是粗糙的 `lng*2-out[0]` 近似。包尚未加入 `app/pubspec.yaml`——转换代码属 M1 定位功能，写那段代码时再引入，不提前挂依赖。

- **D4　真实住址、精确坐标、POI UID 不进仓库**，按 `docs/GIT_COMMIT_RULES.md` §3 处理；M0 探针通过 `tools/build_probe.sh` 以 `--dart-define` 构建期注入，未注入时使用虚构示例点。

## 后果

- **D3 与 P0-2 解绑（2026-11-12 更新）。** 原先后果是「geoconv 需要 AK，不申请移动端 AK 就做不了起点转换」。事实 7 的交叉验证通过后，起点转换变成纯本地计算，**不需要任何 AK、不需要网络**。这条不再阻塞 D3，也不再是 P0-2 的前置条件。

- 若 O1/O2 证明百度会自动取当前位置，V1 可以不申请定位权限、不做坐标转换，D3 降级为「仅当显式传起点时才需要」。这会显著缩小 V1 范围，仍是 M0 最值钱的结论之一——**但即使 O1/O2 成立，D3 也不再是风险项**，两条路都走得通。

- 事实 1 意味着**不能靠 API 参数自证坐标系**，只能靠 model=5 这类偏移比对。后续新增地点时应复用同一套核验方式，而不是相信 `ret_coordtype`。
