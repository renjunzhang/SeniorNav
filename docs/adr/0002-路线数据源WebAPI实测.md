## 1. 背景

方案 §4.2 要在两条路里选一条：A. Web API + 无服务器函数代理；B. 百度 Android SDK 本地检索。
判断依据是「字段够不够、延迟能不能接受」。§10 的 M0 任务 1 要求先用 Web API 查三条真实线路
（直达、换乘、地铁），记录字段、耗时、配额。本 ADR 是任务 1 的产出。

三条线路的起终点全部取公共地标（合肥南站、合肥火车站、大蜀山国家森林公园、安徽省立医院），
因此录制的 fixture 可以提交。`tools/baidu_direction.py` 的 `save_fixture()` 会在落盘前扫描
`tools/.env.places` 里的真实住址坐标与 POI UID，命中即拒绝写入——fixture 目录不在 `.gitignore` 里，
光靠注释拦不住有人把 ROUTES 改成真实住址再录一遍。

匹配精度取 **6 位小数以上**（约 0.1 米）。最初连 3–4 位一起拦，结果安徽省立医院的经度
三位小数前缀与家的相同，两份正常的公共地标 fixture 被判成隐私泄露。
闸一旦天天误报就没人看了，因此宁可只拦高精度值。

## 2. 实测结论

### 2.1 延迟远低于 §6.2 的 3 秒预算

| 接口 | 实测（单请求） |
|---|---|
| `direction/v2/transit` | 227–662 ms |
| `direction/v2/walking` | 180–337 ms |
| 两者串行合计 | 约 420–800 ms |

§6.2 要求「点击地点后 3 秒内（p95）出现摘要」。服务端部分只占 0.4–0.8 秒，
余量足够覆盖定位、渲染与代理转发。**方案 §3.2 的「并行查询公交与步行」是可行的，
但见 2.6 的并发约束。**

曾出现一次 walking 请求 25 秒超时（约 120 米的短途 OD）。复测同一 OD 为 180 ms，
未复现；同期平台发来并发告警短信，判断是并发争用导致的一次性排队，不是接口特性。

### 2.2 配额：路线规划服务并发上限是 3

平台短信原文（2026-11-12）：

> 您账号使用的**路线规划服务并发量已接近约定上限（3/3）**，为不影响正常使用，请登录官网提交工单。

个人开发者认证的服务端 AK，路线规划服务只有 **3 并发**。当日总配额未能确认——
控制台会话已过期，跳转登录页，需要用户自行登录查看。

这条直接约束 §4.2 的 A 路设计：

- §3.2「并行查询公交与步行」一次占 2 个并发槽；
- §4.3「若换乘 > 1，再用少换乘策略查一次」**必须等前两次返回后再发**，不能并行，否则占满 3 槽；
- **客户端超时不会释放服务端并发槽**。`tools/baidu_place.py` 的 `signed_get(timeout=…)` 到点只断开本地连接，
  服务端可能仍在处理。因此 §4.2 要求的「超时 3 秒 + 失败回退」之后**不能立刻自动重发同一请求**，
  否则一个卡住的请求加上重试就能耗尽全部 3 个槽；
- V2 若支持多个家庭同时使用，3 并发不够，需提交工单提额或改走 B 路。

**批量 ≠ 并发。** 一个请求里带多组参数只占 1 个槽。坐标交叉验证工具
`tools/coord-check/crosscheck.py` 据此设计：`conv()` 是阻塞 `for` 循环，一次只发一个请求，
**并发恒为 1**；每个请求最多带 `CHUNK = 10` 组坐标，一次完整运行共 **11 个** `/geoconv/v2/`
请求（反解迭代 4 + 收敛校验 1 + bd09→gcj02 1 + model=2 两批 2 + model=1 1 + 归因 model=5 两批 2）。
失败即 `sys.exit`，不重试，避免卡住的请求叠加新请求耗尽槽位。
注意短信只点名了**路线规划服务**，坐标转换服务的并发上限**未确认**，所以这里保持串行而不是压到 3。

### 2.3 §4.3 的响应结构描述不准确，照它写解析会直接崩

方案 §4.3 写「公交响应包含 `duration`、`distance`、`steps`、`vehicle_info`；`vehicle_info` 有线路
`name`、`type`、`stop_num`、`on_station`、`off_station`、首末班时间、终点站名」。实测结构是：

```text
result.routes[]                       # duration / distance / price / price_detail / arrive_time / steps
  └─ steps[]                          # ← 列表的列表，不是对象数组
       └─ [segment]                   # trans_type / distance / duration / instructions / path
                                      # start_location / end_location / traffic_condition / tip_text
            └─ vehicle_info           # ← 只有 {type, detail} 两个键
                 └─ detail            # name / type / bus_type / direct_text / stop_num / stop_info[]
                                      # on_station / off_station（纯字符串，不是对象）
                                      # first_time / last_time / line_id / line_color
                                      # start_info{} / end_info{} / shuttle_time_table[]
```

三处会导致代码失败的偏差：

1. `routes[].steps` 是**列表的列表**，`step.get(...)` 抛 `AttributeError`；
2. 线路字段全在 `vehicle_info.detail` 里，`vehicle_info` 这一层只有 `type` 和 `detail`；
3. `on_station` / `off_station` 是**纯字符串**，不是 `{name: …}` 对象。

另有两个 `type` 字段，含义完全不同，§4.3 把它们混为一谈：

| 字段 | 观测值 | 含义 |
|---|---|---|
| `vehicle_info.type` | 3 / 5 | **分段类型**：3=乘车段，5=步行段或「同站换乘」标记（`detail` 为 null） |
| `vehicle_info.detail.type` | 0 / 1 | **线路类型**：0=普通公交，1=地铁/轻轨（与 §4.3 的描述一致） |

判定乘车段应以 `detail` 是否为 null 为准，`trans_type` 作辅助（0=步行，-1=乘车，3=同站换乘）。

### 2.4 「开往方向」必须取 `direct_text`，取 `end_name` 会指错方向

§4.4 把 `direction` 字段注为「开往方向（终点站名）」，§4.3 称 `vehicle_info` 含「终点站名」。
实测这两个字段是不同的东西：

```text
轨道交通1号线   direct_text = "张洼方向"        ← 真正的行车方向（线路终点站）
                end_info.end_name = "合肥火车站" ← 本次行程的下车站
                off_station = "合肥火车站"       ← 与 end_name 完全相同
```

`end_info.end_name` 就是下车站，不是线路终点站。若按 §4.4 的字面描述实现，摘要会印出
「坐 轨道交通1号线（开往 **合肥火车站** 方向）」，而列车实际开往**张洼**——
这正是 §8 风险表里「摘要与百度地图方案不一致 → 老人按摘要坐错车」和 §6.4 V2 门槛
「未出现指错方向/错站的阻断问题」要防的失效模式。

**`RouteSummary.direction` 必须映射 `vehicle_info.detail.direct_text`。**

### 2.5 `stop_num` 语义已确认，§3.3 的措辞限制可以解除

§3.3 明确要求：「站数写成『坐 6 站』之前，必须确认 `stop_num` 的语义（是否含上/下车）；
未确认前写『6 站左右』或直接省略」。

实测 4 个乘车段，`stop_num` 与 `stop_info`（中途站列表）的长度关系全部成立：

| 线路 | stop_num | 中途站数 | stop_num == 中途站数 + 1 |
|---|---|---|---|
| 轨道交通1号线 | 10 | 9 | ✓ |
| 85路 | 8 | 7 | ✓ |
| 320路 | 10 | 9 | ✓ |
| 23路 | 2 | 1 | ✓ |
| 509路 | 4 | 3 | ✓ |

即 `stop_num` = **站间数**（不含上车站，含下车站），与百度自己在 `instructions` 里写的
「经过 N 站」一致。因此「坐 10 站」是正确表述，无需降级为「10 站左右」。

附带收获：`stop_info[]` 给出每个中途站的站名与坐标，可用于交叉校验，也可在摘要里做
「还有 N 站」这类展开（本期不需要）。

### 2.6 `tactics_incity` 枚举与方案一致，但与 URI 的 `sy` 枚举编号冲突

用同一 OD 对逐个取值实测（合肥南站-地铁站 → 合肥火车站）：

| tactics_incity | 返回首条方案 | 时长 | 换乘 | 步行 | 方案数 |
|---|---|---|---|---|---|
| 0 | 轨道交通1号线 直达 | 28.9 min | 0 | 315 m | 5 |
| 1 | 轨道交通1号线 直达 | 28.9 min | 0 | 315 m | 4 |
| 2 | 23路 + 509路 | 49.4 min | 1 | 265 m | 5 |
| 3 | 23路 + 509路 | 49.4 min | 1 | 265 m | 5 |
| 4 | 轨道交通1号线 直达 | 28.9 min | 0 | 315 m | 5 |
| 5 | 轨道交通1号线 直达 | 28.9 min | 0 | 315 m | 4 |

0=推荐、1=少换乘（方案数变少）、2=少步行（步行最短但改成公交）、3=不坐地铁（结果无地铁）、
4=时间短、5=地铁优先。**§4.3 的枚举表是正确的。**

但百度地图 **URI API 的 `sy` 参数用的是另一套编号**：0 推荐、2 少换乘、3 少步行、
4 不坐地铁、5 时间短、6 地铁优先（没有 1）。同一个数字在两个接口里含义不同：

- `tactics_incity=2` → 少步行
- `sy=2` → 少换乘

V1 同时使用两个接口（Web API 出摘要，URI 调起导航），**绝不能共用一个常量**，
否则摘要按少步行算、打开的地图按少换乘算，两者给出不同方案，而摘要页还写着「以百度地图为准」。

### 2.7 默认策略 `tactics_incity=2` 应当改掉（修订 §10 的 D2）

§4.3 与 §10 D2 都把默认值定为 2（少步行）。实测这条策略对老人是净损失：

| OD | tactics | 时长 | 步行 | 换乘 |
|---|---|---|---|---|
| 大蜀山森林公园 → 安徽省立医院 | 0（推荐） | **39.9 min** | 1302 m | **0** |
| 同上 | 2（少步行） | 87.6 min | 862 m | 1 |

少步行省下 440 米，代价是多花 47.7 分钟、多换 1 次车。而 §4.4 自己规定的排序是
「**先比较换乘次数，再比较步行距离，最后比较时长**」，§3.3 也写「先写不用换车 / 要换 1 次车，
**这是老人最关心的信息**」。**方案的 API 默认值与方案自己的摘要排序规则相互矛盾。**

更糟的是 §4.3 的补救条件不会触发：「若换乘 > 1，再用 1（少换乘）查一次」——
这里换乘数恰好是 1，不满足 >1，于是这条 87.6 分钟的方案会被直接展示给老人。

建议默认改为 **0（推荐）或 1（少换乘）**，并把补救条件改成「若换乘 ≥ 1」。最终取值应在
§6.3 测试矩阵的 12 类场景上比对后再定。

### 2.8 「status=0 但 routes 为空」是一个必须单独处理的分支

约 95 米的短途 OD（合肥南站 → 合肥南站-地铁站），transit 返回：

```json
{"status": 0, "message": "成功", "result": {"routes": []}}
```

**状态码是成功，但没有任何方案。** §3.4 的规则「没有公交方案 → 走路（并提示距离）」
对应的正是这条路径。若代码只判断 `status != 0` 为失败，这种情况会被当成成功并渲染出空白摘要。

判据必须是 `status == 0 && routes.isEmpty` → 无公交方案，而不是错误。
fixture `walk_short_transit.json` 就是为这个分支录的。

### 2.9 首末班时间返回了，但接口不会替你判断「现在有没有车」

查询发生在**本地时间约 02:00**，返回的轨道交通1号线 `first_time = "06:12"`、
`last_time = "23:35"`，接口照常给出这条方案，没有任何「当前不在运营时间」的提示。

§3.3 只把首末班时间列为可用字段，没有要求校验。若老人凌晨点「回家」，摘要会告诉他
去坐一班 4 小时后才发车的地铁。**摘要生成时必须用 `first_time`/`last_time` 与当前时间比对**，
不在运营时间内要给出降级文案（例如「现在没有公交，建议打开百度地图」），不能照印。

### 2.10 其余与方案有出入的细节

| 项 | 实测 | 影响 |
|---|---|---|
| `departure_time` | 只接受 `HH:mm`（最长 11 字符）。传 Unix 时间戳 → `status=2 departure_time 参数有误`；传 `YYYY-MM-DD HH:mm:ss` → `最大长度是11` | §4.3 的参数表没列这个字段。按「出发时间」的字面意思传时间戳是必踩的坑，`tools/baidu_direction.py` 默认不传 |
| `destination_uid` | 带与不带，返回方案与耗时完全一致（567 ms vs 565 ms） | §4.3 把它列为关键参数，但在本 OD 上**无可观测差异**。不能据此断定被忽略，只能说未验证出效果 |
| `instructions` | 含 HTML 标签，如 `向正南方向出发,走240米,<b>左转</b>` | 直接渲染会让老人看到 `<b>`。展示前必须去标签 |
| 过街提示 | **没有结构化字段**。步行段有 `turn_type_id`/`direction`/`type`，但无过街标志。只能在 `instructions` 文本里匹配（26 段中命中「天桥」2 次；19 段中命中「马路」1 次；95 米那条 0 命中） | §3.3 写「是否需要过街提示（来自百度 steps）」，实际只能靠关键词猜测，属尽力而为，不能作为可靠信息展示 |
| 站名 | 含出入口字母，如 `合肥南站(C口)`、`大蜀山站(C口)` | 对老人有用，但 §3.3「站名不截断、长名称换行」的排版要按这个长度设计 |
| `route` 其他字段 | `price`、`price_detail`、`arrive_time`；`result` 层还有 `taxi`、`total` | §4.4 的 RouteSummary 未包含。票价对老人有价值，建议评估是否加入 |
| 命名风格 | walking 的 `route` 用 camelCase（`originLocation`/`destinationLocation`），transit 用 snake_case | 解析层不能复用同一套字段名 |

### 2.11 换乘步行与「同段备选线路」：两处会让摘要少算步行、多算换乘

修解析器时在同一份 fixture（`app/test/fixtures/metro_direct_transit.json`）里发现两个此前没记录的结构事实。

**（1）`trans_type == 4` 是换乘步行，不是标记。** 第 4/5 条方案的两段乘车之间夹着
`instructions` 为「步行228米」/「步行338米」的段，`trans_type` 是 4。
旧实现只累加 `trans_type == 0`，把这两段整段丢掉：

| 方案 | 正确 walkM | 旧实现 walkM | 丢失 |
|---|---|---|---|
| `routes[3]` | 2213 + 228 + 82 = 2523 | 2295 | 228 米 |
| `routes[4]` | 2213 + 338 + 386 = 2937 | 2599 | 338 米 |

后果不只是数字偏小：`boardWalkM` 归零会让摘要里「步行约 230 米 → 上车站」**整行消失**，
老人不知道换乘还要走一段。而 §4.4 选路的第二关键字就是步行距离，少算 338 米足以改变排序。
`trans_type == 3` 仍是同站换乘标记（distance 恒为 1 米），继续不计入。

**（2）同一组里的多条车辆段是「这一段可任选其一」的备选线路。** `routes[4]` 的一组里并列
4路 / T38路 / T37路 / T12路 四条 `detail`，四段 distance 之和 **19081 米 > 整条 `route.distance` 14114 米**
——连续乘车不可能超过总里程，因此它们是同段备选。旧实现给每条 `detail` 建一个 leg，
把 1 次换乘算成 3 次，摘要会印「要换 3 次车」，实际只需换 1 次。

实现上必须**保留组边界**（`steps` 的外层列表），每组只取第一条车辆段；
把 `steps` 拍平成一个段列表就再也分不出「备选」与「换乘」。

两条都已写成回归测试（`app/test/baidu_route_parser_test.dart`）。修复后重跑
`app/tool/render_paper_summary.dart`，输出与 `docs/m0/纸面摘要样张.md` 逐字一致
——样张选中的三条方案都不含这两种形状，所以朗读材料不需要重印。

### 2.12 解析对了不等于展示对了：换乘步行在渲染层第二次丢失

§2.11 修的是解析层（`walkM` / `boardWalkM` 算对）。2026-11-12 复查渲染层，发现同一批数据在文案里**第二次丢失**：`_renderTransit` 只为首段渲染独立步行行，后续段的 `boardWalkM` 既不进换乘行、也不进「到终点」行——后者用 `walkM − Σ boardWalkM` 已经把它扣掉了。

| 方案 | walkM | 各段 boardWalkM | 修复前文案里的步行 | 隐形段 |
|---|---|---|---|---|
| `metro_direct routes[1]` | 941 | 60 / 495 | 60 + 390 | **495 米** |
| `metro_direct routes[3]` | 2523 | 2213 / 228 | 2200 + 80 | **228 米** |
| `metro_direct routes[4]` | 2937 | 2213 / 338 | 2200 + 390 | **338 米** |

老人看到的是「下车后走 390 米到终点」，实际还要先走 495 米去换车。这与 §2.11 的后果同级，只是发生在渲染层。

**修复**：换乘步行并进换乘行——「③ 步行约 500 米，换 省二院健康专线（开往 仁济医院方向），5 站，站前广场站下车」，**不单独占行**：4 行预算下单独一行会把「换哪路车」挤掉（`bus_transfer routes[2]` 已经因 2 次换乘触发截断）。同站换乘（`boardWalkM == 0`，如 `bus_transfer routes[0]`）不加前缀，不写「步行约 0 米」。

**回归测试 4 个**（`app/test/route_summary_test.dart`）：换乘行文案逐字、「到终点」不重复计入、0 米不写、**未截断方案的步行米数之和与 `walkM` 守恒**（容差按取整粒度 60 米/段）。最后一条是通用不变量：将来新增步行段类型或改渲染顺序，都会被它拦住。截断方案按 §3.3 主动丢弃细节，不参与守恒校验。

纸面样张因此新增**样张 4（1 次换乘方案，非推荐）**：前三张推荐方案都是 0 换乘，朗读测试里「要不要换车/换几次」「下车之后还要走多远」两问原本测不到。

### 2.13 绕路阈值在真实 fixture 上的复核（A11）

A11 的 10 分钟 / 2 倍此前只有构造数据验证。2026-11-12 用两份真实 transit fixture 逐条跑过滤：

| fixture | 最快 | 最短 | 时长门槛 | 里程门槛 | 结果 |
|---|---|---|---|---|---|
| `metro_direct`（5 条） | 28.9 min | 10953 m | ≤38.9 min | ≤21906 m | 只有 `routes[0]`（28.9 min / 0 换乘）双过；其余 4 条**全部被时长淘汰**，里程门槛一条都没淘汰 |
| `bus_transfer`（5 条，`tactics_incity=2` 录制） | 39.9 min | 11323 m | ≤49.9 min | ≤22646 m | 只有 `routes[4]`（39.9 min / 0 换乘）双过；百度原顺序第一条是 87.6 min / 1 换乘，**被时长淘汰** |

三条结论：

1. **真实数据上时长过滤是唯一起作用的门槛**，里程 ×2 在这两份 fixture 里从未淘汰任何方案（最远 15962 m < 22646 m）。里程过滤的价值目前只有构造数据证明，**不能声称已被真实数据验证**。
2. 「过滤后为空则退回时长过滤」这条兜底路径在真实数据上**也没触发过**，同样只有构造数据覆盖。
3. 绕路保护在 `bus_transfer` 上确实改变了结果：不加重排会选中 87.6 分钟 / 1 换乘，加了之后选 39.9 分钟 / 0 换乘，**省 47.7 分钟**。这是 A11 值得保留的真实证据。

`walkM` 目前只是排序的第二关键字，**不是过滤条件**——§4.4「步行远的方案直接淘汰」还没有落地口径。`metro_direct routes[2]`（0 换乘但步行 2308 米）在本例中被时长门槛顺带淘汰，属巧合而非设计。是否要给步行加独立阈值，等 §6.3 的 12 类场景跑完再定，现在加就是无证据的猜测。
