## 0. 结论速览

**现有架构不需要调整；只有一处选型微调（Drift → sqflite），且发生在写代码之前，重构成本为零。** `RouteSummary` 领域模型与数据源分离的分层（`app/lib/route_summary.dart` ← `app/lib/baidu_route_parser.dart`）在本次调研中被反复验证是正确的：三个候选"成熟方案"都在数据源层有硬缺陷，而没有一个能替代已经写好的摘要模型与文案规则。

五条最重要的结论，全部来自源码而非 README：

| # | 结论 | 证据 |
|---|---|---|
| 1 | **官方 `flutter_baidu_mapapi_search` 不能直接用于路线摘要**：它在 Java 桥接层丢弃了 `direct_text`，Dart 侧完全拿不到"开往方向"。这正是 ADR 0002 A2 的安全红线 | §3.2 |
| 2 | **`map_launcher` 不能替代 `app/lib/baidu_uri.dart`**：`coord_type` 硬编码 `gcj02`，与 ADR 0001 D1 的 BD-09 全链路冲突，且 extras 冲突会抛异常，无法覆盖 | §5 |
| 3 | **Trufi Core 不引入**：GPL-3.0 + 强绑 OpenTripPlanner/GTFS + 无任何已发布 pub 包；其地图中心 timeline 对"6 行纯文本"是过度设计 | §4 |
| 4 | **`coordtransform_dart` 是最该优先引入的包**：它把 ADR 0001 D3 的起点转换从"需要 AK 的网络接口"降级为纯本地计算，直接解开 D3 与 P0-2 的绑定 | §7.1 |
| 5 | **持久化应改用 `sqflite`，不用方案既定的 Drift**：官方 2 列示例生成 367 行代码，16 列表≈1500 行；而 drift 的三大收益对"20 行单表"全部为零，还要构建期从 GitHub 下载 `.so` | §6.3–§6.6 |

两个反向发现：

- **`flutter_bmflocation` 的 AndroidManifest 声明了 `ACCESS_BACKGROUND_LOCATION` 与 `READ_PHONE_STATE`**，会合并进 APK，直接违反方案 §6.2 验收第 9 条"无后台定位权限"。见 §7.2。
- **适老化 UI 没有成熟开源包可复用**，pub.dev 上的 "senior" 包是巴西 HR 产品。但 Flutter 内置的 `MediaQuery.withClampedTextScaling` 一行就能守住"1.3× 不溢出"，**运行时零新增依赖**；只加 `accessibility_tools` 作 dev_dependency 自动检查 72dp。见 §6.7–§6.8。

### 1.1 取证方式

- **百度系插件没有公开 GitHub 仓库**。`gh search repos flutter_baidu_mapapi` 只返回第三方 fork（最高 8 stars，且多为 map 组件）。官方 `homepage` 指向 `lbsyun.baidu.com` 文档站。因此本次直接下载 **pub.dev 发布包 tarball**——它包含完整的 Dart、Android Java、iOS Objective-C、鸿蒙 ETS 源码，等价于读仓库源码。

## 3. 百度地图 Flutter 插件（重点）

### 3.1 制品与维护：维护非常活跃，但治理不透明

四个组件同日发布 4.0.2+1（2026-11-06），CHANGELOG 显示节奏是每几周一个版本，且已支持鸿蒙（`ohos` pluginClass）。**维护状态是本次调研中最好的一档**。

但有两个治理层面的问题：

1. **无公开源码仓库、无 issue tracker**。`homepage` 是文档站，POM/pubspec 里没有可提 issue 的地方。发现缺陷（如 §3.2）只能自己 fork 或绕开，无法上报后等修复。
2. **插件 pin 的原生 SDK 落后于 ADR 0003 探针的版本**：插件用 `BaiduMapSDK_Search:8.2.0`，ADR 0003 静态探针用的是 `9.0.0`。两者 `BusInfo` 的 getter 表面一致（§3.2 已复核 8.2.0），但**不是同一制品**，ADR 0003 的 sha256 与体积数字不能直接套到插件上。

原生依赖（`android/build.gradle`）：

| 组件 | 原生依赖 | minSdk | 备注 |
|---|---|---|---|
| base | `com.baidu.lbsyun:base:8.2.0` | 22 | 传递依赖 |
| search | `BaiduMapSDK_Search:8.2.0` + `gson:2.8.6` | 22 | **与 ADR 0003 同一 Maven 坐标** |
| utils | `BaiduMapSDK_Util:8.2.0` + `gson:2.8.6` | 22 | |
| map | `BaiduMapSDK_Map:8.2.0` + **`android.arch.lifecycle:extensions:1.1.1`** + `androidx.localbroadcastmanager:1.0.0` | 22 | 见 §3.6 |

工程 `minSdk` 24 ≥ 22，满足。三个非 map 组件的 AndroidManifest **零权限声明**（实测 `cat` 均为空 manifest），与 ADR 0003 §4 的结论一致。

> **副作用需知情**：search/utils 的 `build.gradle` 里有 `rootProject.allprojects { repositories { maven { url 'https://maven.aliyun.com/repository/...' } } }`，会把阿里云镜像注入**整个工程的所有模块**，不只是插件自己。这会影响依赖解析来源，属供应链层面应当知情的改动。

### 3.2 决定性缺陷：`direct_text` 在 Java 桥接层被丢弃

这是本次调研最重要的发现，直接决定"能不能用官方插件做摘要"。

**证据链（四步，全部可复核）**：

**① 原生 AAR 有这个 getter。** 下载插件所 pin 的 8.2.0 制品，`javap` 实录：

```
public class com.baidu.mapapi.search.core.BusInfo extends TransitBaseInfo {
  public java.lang.String getDirectText();      ★ 存在
  public java.lang.String getLineUid();
  public java.lang.String getStartUid();
  public java.lang.String getEndUid();
  public java.util.List<RouteNode> getPassStopInfoList();
  public int getType();
  public int getStopNum();
}
```

**② 插件的 Java bean 从不调用它。** `android/src/main/java/com/baidu/mapapi/search/bean/result/route/masstransirouteresult/BMFBusVehicleInfo.java:33-37` 是全部赋值逻辑：

```java
public BMFBusVehicleInfo(BusInfo busInfo) {
    super(busInfo);
    this.type = busInfo.getType();
    this.passStationNum = busInfo.getStopNum();
}
```

父类 `BMFMassBaseVehicleInfo.java:34-44` 只取 `getName()` / `getDepartureStation()` / `getArriveStation()` / `getDepartureTime()` / `getArriveTime()`。**`getDirectText()` 一次都没出现。**

**③ Dart 侧没有这个字段。** `lib/src/common/bmf_routevehicleInfo.dart:121-182` 的 `BMFBusVehicleInfo` 字段全集：`name`、`departureStation`、`arriveStation`、`departureTime`、`arriveTime`、`passStationNum`、`firstTime`、`lastTime`、`type`。

**④ 全包 grep 零命中。** 对 search / base / utils / map 四个包的**全部** Dart + Java + Objective-C + ETS 源码执行 `grep -rn -i "directtext|direct_text"`，**结果为空**。

**⑤ 没有原始 map 逃生口。** 回调是强类型的 `typedef BMFOnGetMassTransitRouteResultCallback = void Function(BMFMassTransitRouteResult, BMFSearchErrorCode)`（`lib/src/private/bmf_routesearch_dispatcher.dart:15-16`），拿不到未经 bean 裁剪的原始 JSON。

**后果**：用官方插件做公交摘要，"开往方向"这一项**必然缺失**。而 `arriveStation` 是**下车站**，不是线路终点站——ADR 0002 §2.4 已经实测过这个陷阱（`direct_text="张洼方向"` 而 `end_name="合肥火车站"`）。若退化用 `arriveStation` 冒充方向，就会精确复现 ADR 0002 A2 与方案 §8 风险表要防的失效模式：**老人按摘要坐反方向的车**。

方案 §3.3 把"线路名 + 方向"列为公交摘要的必备内容，§6.4 的 V2 门槛是"未出现指错方向/错站的阻断问题"。**这不是可以降级绕过的字段。**

**补救成本（已核实可行，但有维护代价）**：结果 bean 是整体 gson 序列化的——`RouteLineSearchHandler.java:419` `mGson.toJson(bmfMassTransitRouteResult)`，因此给 Java bean 加一个 public 字段就会自动传到 Dart。修复只需约 6 行：

- `BMFBusVehicleInfo.java`：加 `public String directText;` + `this.directText = busInfo.getDirectText();`
- `bmf_routevehicleInfo.dart`：加字段声明 + `fromMap` + `toMap` 各一行

BSD-3-Clause 允许 fork。但这意味着**长期维护一个偏离上游的分支**，而上游每几周发一版。对单人开发是真实负担。

**被否决的替代绕法**：`BMFBusLineResult.busLineDirection` 确实存在（`lib/src/model/bmf_buslinesearch_result.dart:13`），但 `BMFBusLineSearchOption.busLineUid` 是 **required**（`bmf_buslinesearch_options.dart:25`），而 `BMFBusVehicleInfo` **没有 uid 字段**——原生 `getLineUid()` 同样被插件丢弃（grep 零命中）。按线路名反查会命中双向线路中的一条，方向不可靠。**不能用来补安全关键字段。**

### 3.3 其他字段缺口与命名陷阱

按 ADR 0003 的 13 个模型字段逐项核对插件 Dart 表面：

| 模型字段 | 原生 getter（8.2.0 已复核） | 插件 Dart | 判定 |
|---|---|---|---|
| `lineName` | `getName()` | `.name` | 可用 |
| `lineType` | `BusInfo.getType()` | `.type`（注释"Android独有"） | 可用，语义未验证 |
| **`direction`** | **`getDirectText()`** | **无** | **不可用（红线）** |
| `boardStop` | `getDepartureStation()` | `.departureStation` | 可用 |
| `alightStop` | `getArriveStation()` | `.arriveStation` | 可用 |
| `stopCount` | `getStopNum()` | `.passStationNum` | 可用 |
| `firstTime` | `TransitBaseInfo.getDepartureTime()` | `.departureTime` | **可用但名字误导**，见下 |
| `lastTime` | `TransitBaseInfo.getArriveTime()` | `.arriveTime` | **同上** |
| `boardWalkM` | 步行 step `getDistance()` | `BMFWalkingStep.distance` | 可用 |
| `durationSec` | `RouteLine.getDuration()` | `BMFTime duration` | 可用 |
| `distanceM` | `RouteLine.getDistance()` | `.distance` | 可用 |
| `walkM` | 步行段求和 | 需自行遍历 | 可用 |
| `crossingCount` | `WalkingStep.getInstructions()` | `BMFWalkingStep.instruction`（**单数**） | 可用 |
| `arriveTime`（附带） | `MassTransitRouteLine.getArriveTime()` | **无** | 不可用（仅展示，影响小） |
| `stop_info` 交叉校验 | `getPassStopInfoList()` | **无** | 不可用 |

**首末班的命名陷阱（务必按此映射，否则运营时段校验会失效）**：

- Java bean 里 `firstTime` / `lastTime` 两个字段注释写的是 **"iOS独有"**（`BMFBusVehicleInfo.java:20-30`），且**Android 构造函数从不给它们赋值** → **Android 上恒为 null**。
- 但首末班数据**并没有丢**：它藏在父类的 `departureTime` / `arriveTime` 里。ADR 0003 §3 的字节码证据是 `first_time → setDepartureTime`、`last_time → setArriveTime`。
- 而 Dart 侧注释恰好写反了：`/// 出发时间(BMFBusVehicleInfo时departureTime为空)`（`bmf_routevehicleInfo.dart:77`）。**照 Dart 注释实现会认为公交段没有首末班，从而跳过 ADR 0002 A7 要求的运营时段校验**——凌晨 2 点给老人推荐 4 小时后才发车的地铁。

即：插件的 Dart 文档在这一点上**与 Android 实现相反**。这是"只读 README/文档不读源码"必然踩的坑。

**一个正面发现**：`BMFMassTransitStep.isSubStep`（`bmf_routestep.dart:183-191`）显式区分"子路段（A→B 经过多个 steps）"与"多个方案（A→B 有多个选择）"。这与 `app/lib/baidu_route_parser.dart` 里 `_transitGroups` + `rideTaken` 辛苦发现的"同组多条车辆段是备选线路、不是连续乘车"语义**完全对应**。说明现有解析器的核心洞察在 SDK 路径上同样成立，不需要重新发现。

**策略枚举**：`BMFMassTransitIncityPolicy`（`bmf_routesearch_type.dart:75-93`）六个值顺序为 RECOMMEND / TRANSFER_FIRST / WALK_FIRST / NO_SUBWAY / TIME_FIRST / SUBWAY_FIRST，**与 ADR 0002 §2.6 实测的 `tactics_incity` 0–5 逐项一致**。这是好事，但也意味着 ADR 0002 A4 的"两套枚举不能共用常量"要升级为**四套**（见 §3.5）。

### 3.4 插件真正有价值的部分：POI / Suggestion 检索

路线检索不能用，但**地点检索这一半是合格的**，而且正好命中 V1 尚未开工的最大块工作。

`BMFPoiDetailInfo`（`lib/src/common/bmf_poisearch_type.dart`）暴露了：

- **`naviLocation`**（:207）——导航终点坐标。Android 侧 `PoiDetailDetailResultBean.java:100` 确实调用 `poiDetailInfo.getNaviLocation()`，iOS 侧 `BMFPoiSearchType.m:126` 同样有。**直接满足 ADR 0001 D2「导航终点存 navi_location，不存 location」**。
- **`children`**（:258，`List<BMFPOIDetailChildrenInfo>`）——出入口子点，含 `uid`（:375）与 `distance`（:198）。**满足 ADR 0001 D2 附带要求「额外记录 pv_rate 最高的那个门（含其 uid）」**的数据来源。
- `uid` / `name` / `address` / `city` / `province` / `area` / `adcode` / `pt` / `parentPOI`——覆盖方案 §4.6 地点模型的全部 POI 侧字段。

插件同时提供 `BMFSuggestionSearch`（输入提示）与 `BMFPoiSearch`（地点检索），正好对应方案 §3.6 的"搜索 → 选择 → 地图确认入口"三步的前两步，以及附录 A 里"suggestion 给 15 位小数精确坐标、v2/search 只给 6 位"的实测结论。

**复用价值**：省掉自建 POI 检索的 HTTP 层 + 签名 + 解析 + 平台通道，约等于方案 §4.6 地点录入的整个数据侧。

**代价**：一旦引入，就付掉了 B 路的全部固定成本——Android 端 AK（绑定包名 + SHA1）、`SDKInitializer.setAgreePrivacy` 隐私合规门槛、原生 `.so`（ADR 0003 测得 arm64 约 3.1 MiB）。base 组件已暴露 `setApiKey(String, BMF_COORD_TYPE)` 与 `setAgreePrivacy(bool)`（`lib/src/map/bmf_map_sdk.dart:17,44`），ADR 0003 §4 的合规硬门槛在 Dart 侧有对应 API，不需要自己写通道。

> **注意这会造成混合架构**：POI 走 SDK（需 Android AK），路线走 Web API（需服务端 AK + 代理）。**两个 AK、两条数据通路**，比纯 A 或纯 B 都复杂。是否值得，取决于 D1（见 §3.7）。

### 3.5 `utils` 调起：不能替代 `baidu_uri.dart`

`BMFOpenMapUtils` 提供 `openBaiduMapNavi` / `openBaiduMapRoute` / `openBaiduMapPoiDetail` 等（`lib/src/utils/bmf_utils_open_map.dart:17-57`）。看似正好对应 `NavigationLauncher`，但读 Android 实现后结论是**不引入**：

它走的是**百度 SDK 的 `BaiduMapRoutePlan` / `BaiduMapNavigation` 工具类**，不是自己拼 URI（`OpenBaiduRouteHandler.java:88-106`、`OpenBaiduMapNaviHandler.java:96-108`）。因此：

| 能力 | `app/lib/baidu_uri.dart` | `flutter_baidu_mapapi_utils` |
|---|---|---|
| `coord_type` 显式控制 | 有（默认 `bd09ll`） | **无参数**，由 SDK 内部决定 |
| `destination_uid` | 有 | 有（`endUid`） |
| `sy` 策略 | 有，且与 `tactics_incity` 分开定义 | 有 `transitPolicy`，但经内部重映射（见下） |
| `index` / `target` 直达线路详情 | **有**（M0 探针 C 的关键） | **无** |
| 省略 origin 试探自动定位 | **有**（M0 探针 O1/J） | `startCoord` 是 required 参数（可显式传 null） |
| 步行导航的网页回退 | **有**（`webFallback`） | **无**——Dart 注释明写"步行、骑行导航设置该参数无效"（`bmf_open_navi_options.dart:126`） |
| 不依赖原生 SDK / AK | **是** | 否（`BaiduMapSDK_Util` + AK） |
| 可在无真机环境单元测试 | **是**（`app/test/baidu_uri_test.dart`） | 否 |

**第三套策略枚举**：`BMFOpenTransitPolicy`（Dart，5 个值）在 `toMap()` 里发送 `index + 3`（`bmf_open_route_options.dart:128-130`，注释"native 初始值为3"），Android 侧 `correctBusStrategy` 再 `-= 3` 并交换 0↔4（`OpenBaiduRouteHandler.java:145-154`）。两边抵消，**不会崩**，但最终落到 SDK `EBusStrategyType` 的哪一项**在插件源码里看不出来**（在 Util AAR 内部）。结论：**不能假设 Dart 枚举序号等于 URI 的 `sy` 值**。

加上 §3.3 的 `BMFMassTransitIncityPolicy`，ADR 0002 A4 的"两套枚举"实际是**四套编号**：`tactics_incity`（Web API）、`sy`（URI）、`BMFMassTransitIncityPolicy`（插件检索）、`BMFOpenTransitPolicy`+SDK 重映射（插件调起）。**现有 `baidu_uri.dart` 自己掌握 URI 构造，反而是最可控的一套。**

**唯一值得吸收的事实（参考源码价值）**：`bmf_open_navi_options.dart:9-22` 的版本门槛注释——

- `WalkNavi`：**百度地图客户端 v8.8 以后支持**
- `ARWalkNavi`：客户端 v9.7.5 以后；**低于 8.6.9 不支持步行导航**

方案 §3.7 的失败表有"百度地图未安装"，**但没有"百度地图版本过旧"这一行**。老人手机上的百度地图很可能是长期未更新的旧版本，`walknavi` 会静默失败。建议把这条补进 §3.7 与 M0 任务 4 的记录项（记百度地图版本号）。这是本次调研对现有方案最直接的一条补充。

### 3.6 `map` 组件：体积与遗留依赖双重问题

方案 §3.6 要求"在地图上确认一次入口"，这是唯一需要地图视图的场景。但：

- ADR 0003 已测：Map 组件 `.so` 全 ABI **71.9 MB**、仅 arm64 **18.4 MB**。当前 release APK 48.0 MB。**为"每个地点确认一次"的低频操作增加 18 MB，性价比极差。**
- 插件 `android/build.gradle` 依赖 **`android.arch.lifecycle:extensions:1.1.1`**——这是 **AndroidX 之前的 `android.arch` 遗留支持库**，与现代 Flutter Android 嵌入（AndroidX）混用通常需要 Jetifier，是典型的依赖冲突来源。**静态判断，未实测**。
- iOS podspec 声明 `s.platform = :ios, '8.0'` 且 `VALID_ARCHS[sdk=iphonesimulator*] = 'x86_64'`——**不含 arm64 模拟器**，Apple Silicon Mac 上跑模拟器会有问题。V1 只做 Android，但方案 §2 承诺"保留 iOS 适配接口"，这条要记在账上。

**替代建议**：入口确认改用**百度静态图 API**（一次 HTTP 取图）或**直接调起百度地图客户端让家属看一眼**，都不需要引入地图 SDK。前者与现有 `baidu_uri.dart` 的风格一致，且可测试。

### 3.7 与 ADR 0003 的 Android SDK 方案对比

ADR 0003 的 B 路是"自己写平台通道调 `BaiduMapSDK_Search`"。本次调研给它增加了一个对照项：**官方 Flutter 插件包着同一个 Maven 制品**。

| 维度 | 自建平台通道（ADR 0003 的 B 路） | 官方 `flutter_baidu_mapapi_search` |
|---|---|---|
| 原生制品 | `BaiduMapSDK_Search:9.0.0` | 同坐标 `8.2.0` |
| 13 个字段 | ADR 0003 静态确认 13/13 有 getter | **12/13 可得，`direction` 完全丢失** |
| 首末班 | 按 ADR 0003 映射表直取 | 可得，但 Dart 注释与实现相反，易写错 |
| `stop_info` 交叉校验 | 可得 | 丢失 |
| POI `naviLocation` / 门 uid | 需自己写 | **现成** |
| 需要写的代码 | 约 150 行 Kotlin + Dart 通道，只映射需要的 13 个字段 | 0（但 `direction` 要 fork 约 6 行） |
| 引入的无关表面 | 无 | 60 个 Dart 文件，含天气/行政区/建筑/AOI/全景等 13 类检索，SeniorNav 只用 3 类 |
| 上游维护 | 自己维护，但表面极小 | 官方活跃，但无 issue tracker，fork 需长期跟版 |
| 隐私合规 | `setAgreePrivacy` 需自己调 | Dart 侧已有 API |

**判断**：如果 D1 最终选 B，**自建薄通道优于引入官方检索插件**——因为唯一真正需要的字段恰好是插件丢掉的那个，而自建通道只映射 13 个字段，表面更小、无 fork 负担、可继续用现有 fixture 测试。ADR 0003 已经把最难的活（制品坐标、字段 getter、命名陷阱、合规门槛、体积）做完了，剩下的 Kotlin 量很小。

**但 POI 检索是例外**：如果 D1 选 B 且要做地点录入，插件的 POI 部分（§3.4）确实省事，可以考虑**只用它的 POI/Suggestion，路线仍走自建通道**——两者共用同一个 base 与 AK，不额外增加原生成本。

### 3.8 判断

| 组件 | 判断 | 理由 |
|---|---|---|
| `flutter_baidu_mapapi_search`（路线检索部分） | **不推荐** | `direct_text` 丢失，触碰 ADR 0002 A2 安全红线；首末班 Dart 注释与实现相反 |
| `flutter_baidu_mapapi_search`（POI/Suggestion 部分） | **有条件直接引入**（D1 选 B 时） | `naviLocation` + 门 uid 现成，省掉整个地点录入数据侧 |
| `flutter_baidu_mapapi_base` | **参考源码** | 随 search 传递引入；`setApiKey`/`setAgreePrivacy` 的调用顺序值得照抄 |
| `flutter_baidu_mapapi_utils` | **不推荐** | 无 `index`/`target`、步行无网页回退、需原生 SDK；现有 `baidu_uri.dart` 更强且可测试 |
| `flutter_baidu_mapapi_map` | **不推荐** | arm64 +18.4 MB 换一次低频入口确认；`android.arch` 遗留依赖 |

### 4.3 Saved places：不可抬

`saved_place.dart:27-47` 只有 id/name/address/lat/lon/type/iconName/createdAt/lastUsedAt，**没有** `slot`/`sortOrder`/`verifiedAt`/`deletedAt`/`rev`/`poiUid`/`naviLocation`，坐标是 WGS84 而非 BD-09。持久化是 SharedPreferences 存 JSON 字符串列表。整包依赖 maps + routing + search_locations + go_router，**不可抬**。方案 §4.6 的字段仍需自建。

### 4.4 许可证结论（精确，不夸大）

根 LICENSE 是 GPL-3.0 原文，子包 LICENSE 是指针文件（"Please refer to ../../LICENSE"），**未发现任何宽松许可例外**。

义务触发点是**向他人分发（convey）**：

- **单家庭私有 sideload 属私人使用**，无公开源码义务。
- 严格说，把 APK 递给家庭成员即构成 convey，须向**接收者**提供对应源码（不是向全世界）。
- 一旦 APK 扩散到亲友群/网盘/商店，**整个衍生作品（含 SeniorNav 自有代码）须以 GPL-3.0 提供完整源码**。
- **只读思路、自己重写不构成衍生作品，无 GPL 义务**；逐字复制代码则会传染。

方案 §1.5 写死"单家庭自用、不上架"，所以 GPL 的**现实风险低**；但 §1.5 同时说"如未来要上架，另立专项"——逐字抄码会给那个未来埋雷。**结论：只读不抄。**

## 5. 地图导航调起：`map_launcher`

GitHub：[mattermoran/map_launcher](https://github.com/mattermoran/map_launcher)，MIT，7.0.0（2026-10-14），29 个地图 provider，维护活跃。

**结论：不推荐替代 `app/lib/baidu_uri.dart`。** 三个硬阻塞，全部源码核实：

### 5.1 `coord_type` 硬编码 `gcj02`，且无法覆盖

`lib/src/maps/baidu.dart:89` 与 `:110` 两处都写死 `'coord_type': 'gcj02'`。

SeniorNav 全链路是 **BD-09**（ADR 0001 D1）。把 BD-09 坐标标成 gcj02 会产生数百米偏移——**正是 ADR 0001 要防的 P0-3 失效模式，也正是 M0 探针 L 要量的那个偏移**。

**能否用 extras 覆盖？不能。** `lib/src/utils/launch_helper.dart` 的 `appendQueryParams` 在遇到同名键且值不同时**抛异常**：

```dart
if (values.length != 1 || values.single != entry.value) {
  throw MapConfigurationError(
    'Extra parameter "${entry.key}" conflicts with a URL parameter.',
  );
}
```

CHANGELOG 7.0.0 也明写 "Reject conflicting generated URL parameters"。`BaiduExtra` 只支持 `src` 一个键（`lib/src/extras/baidu_extra.dart:14`）。**这是设计上的拒绝，不是疏漏。**

### 5.2 没有 `walknavi`，也没有百度网页回退

- `BaiduMaps` 只实现 `markerSchemeUrl` 与 `directionsSchemeUrl`，**没有 `walknavi`** → 无法满足方案 §4.5"步行优先直接进语音导航"。
- `directionsUrl`（universal/HTTPS 版本）**直接 `return null`**（`baidu.dart:68-73`），`markerUrl` 同样 `return null`（:65） → **百度完全没有网页回退**，违反方案 §3.7"所有失败路径都必须保留打开百度地图这一条出路"。现有 `baidu_uri.dart:57-82` 的 `webFallback`/`webSearch` 正是为此写的。
- 无 `destination_uid`（丢失 ADR 0001 D2 的出入口精度）、无 `sy`、无 `index`/`target`。

### 5.3 强制要求 origin，挡掉 M0 最值钱的探针

`baidu.dart:56-62` 的 `validateLaunchUrl` 在 origin 为空时**抛 `MapConfigurationError`**。

而 M0 探针 O1/J 就是要测"省略 origin 时百度是否自动取手机当前位置"——ADR 0001 写明这**决定 V1 是否需要申请定位权限**，是"M0 最值钱的结论之一"。用 map_launcher 就做不了这个实验。

（有意思的是 `applyLaunchDefaults` 在 **iOS** 上会自动补 `origin: '我的位置'`（:49-51），与 `baidu_uri.dart:14` 的实测结论一致——但 Android 不补。）

### 5.4 地图检测的复用价值也接近于零

7.0.0 的破坏性变更：**"Remove `MapApp.all` and bundled Android provider queries"**——不再自带 `<queries>` 声明，需 App 自己加（`MIGRATION.md:15-18`）。

而 `app/android/app/src/main/AndroidManifest.xml:42-58` **已经声明了** `com.baidu.BaiduMap` 包与 `baidumap`/`bdapp` scheme，现有 `canLaunchUrl` 检测已经正确。至于 D9（老人机可能只装高德），无论用不用 map_launcher，**都要自己加对应的 `<queries>` 条目**——插件省不掉这一步。

**判断：不推荐。** 现有 137 行 `baidu_uri.dart` + 221 行测试，在参数覆盖、坐标系正确性、网页回退、可测试性四个维度全面优于 map_launcher 的百度实现。**唯一参考价值**：若将来 D9 决定支持高德，`lib/src/maps/amap.dart` 的 `amapuri://route/plan/` 参数构造可以照抄（高德原生就是 GCJ-02，与百度的坐标系处理不同，需分别对待）。

## 6. 常用地点管理：持久化与适老化 UI

### 6.1 先把需求量化，再谈选型

方案 §4.6 的数据模型是**一张表、16 列**（逐行数过：`id`/`slot`/`label`/`icon`/`name`/`address`/`city`/`latitude`/`longitude`/`coordSystem`/`poiUid`/`updatedAt`/`rev`/`sortOrder`/`verifiedAt`/`deletedAt`），`schemaVersion` 是表级而非行级。同节明确"**不保存路线**"，§3.1/§3.5 的规模是首页 4 个 + 更多地点若干，**量级 20 行**。另有一个家属 PIN（§3.6，§4.8 明确"只防误触，不防取证"）。

```
$ExampleTableTable / ExampleTableData / ExampleTableCompanion / _$ExampleDatabase
$$ExampleTableTableFilterComposer / …OrderingComposer / …AnnotationComposer
$$ExampleTableTableTableManager / $ExampleDatabaseManager
```

**2 列 → 367 行。** 按列数线性外推，SeniorNav 的 16 列表约 **1200–1800 行生成代码**（此为推算，非实测）。此外还要引入 `build.yaml`、`drift_schemas/` 快照目录、`database.steps.dart` 迁移辅助，以及生成器与 analyzer 的版本锁——`drift_dev` 2.35.3 钉 `analyzer: >=13.0.0 <15.0.0`，这条约束会参与整个工程的依赖求解。

**drift 买到的三样东西，对一张 20 行的单表收益近乎为零**：

| drift 的能力 | 本项目是否需要 |
|---|---|
| 类型安全 join / 组合查询 | **不需要**：单表，无 join |
| `make-migrations` 自动生成迁移 + 迁移测试 | **不需要**：V1 只有 1 个 schema 版本 |
| stream queries（数据变更自动推 UI） | **不需要**：20 行全量重读 < 1ms，Riverpod 手动 `invalidate` 足够 |

这不是质量问题——drift 维护极好、设计优秀。是**规模不匹配**。

### 6.4 一条容易踩坑的原生依赖变动

`sqlite3_flutter_libs` 已 **EOL**：pub.dev 最新版是 `0.6.0+eol`（2026-02-15），描述原文 **"Not used anymore, update to version 3.x of package:sqlite3 instead"**。`drift_flutter/pubspec.yaml:27-30` 的注释也明写该依赖 **"doesn't do anything"**，保留只是防止用户误依赖 0.5.x。

`sqlite3` 3.x 改用 Dart build hooks：`sqlite3/lib/src/hook/compile/description.dart:67` 默认走 `fromGitHub(LibraryType.sqlite3)`，即**构建期从 GitHub Releases 下载预编译 `.so`**。

对本项目这是实打实的风险：本机是 Clash TUN + 校园网 CGNAT 多出口环境，构建期联网下载二进制既慢又可能失败，而且**给"侧载单家庭 APK"的构建流程凭空加了一个网络前置条件**。

**`sqflite` 完全没有这个问题**：`sqflite_android/android/src/main/java/com/tekartik/sqflite/Database.java:24-32` 直接 `import android.database.sqlite.SQLiteDatabase` 等系统类，全仓库 `find` 不到任何 `CMakeLists.txt` / `.c` / `.so`。**用 Android 系统自带的 SQLite，APK 不增大，构建期不联网。**

### 6.5 sqflite 的迁移能力足够覆盖 V1→V2

- `sqflite_common/lib/sqlite_api.dart:439` 定义 `OnDatabaseVersionChangeFn(db, oldVersion, newVersion)`；`OpenDatabaseOptions` 提供 `version` / `onCreate` / `onUpgrade` / `onDowngrade`。
- **回调在事务内执行**（同文件 :506-507 原文 "They run in a transaction"），迁移失败自动回滚，不会留下半升级的库。
- 另有现成的 `onDatabaseDowngradeDelete`（:480）处理降级。

16 列建表 + 后续 `ALTER TABLE ADD COLUMN` 手写即可；软删除就是 `WHERE deletedAt IS NULL`；`rev` / `updatedAt` / `sortOrder` 都是普通列，方案 §4.6 的"用 `rev` 而非 `updatedAt` 解决冲突"是业务逻辑，与 ORM 无关。

**手写成本约 200 行**（模型 `to/fromMap` ~60 + DAO ~120 + 迁移 ~30，推算），换掉 1500 行生成代码和整条 `build_runner` 链路。在 3–5 周单人预算下这是净省。

### 6.6 持久化判定

| 包 | 判断 | 理由 |
|---|---|---|
| **`sqflite`** | **直接引入** | 零 codegen、零原生、BSD-2、维护活跃（昨天还有提交）、迁移回调带事务。**这是本次调研第二个可无条件引入的包** |
| `drift` / `drift_dev` / `drift_flutter` | **不推荐（V1）** | 规模不匹配（§6.3）+ 构建期下载 `.so`（§6.4）。V2 若真做多表同步，`make-migrations` + schema 快照才有价值；届时迁移成本低，因为 SQL 是纯文本 |
| `shared_preferences` | **不推荐作主存储** | 无 schema / 迁移 / 查询 / 事务，20 行也得自己实现墓碑过滤。PIN 等单值放 sqflite 的 `meta` 表即可，**不必为它多加一个依赖** |
| `hive_ce` | **不推荐** | 同样要 codegen，却丢掉 SQL 与迁移语义 |
| `isar` | **不推荐** | `sdk: ">=2.17.0 <3.0.0"`（已核实），**Dart 3.13 下不可用**；4.x 停在 dev.14（2023-08-21） |
| `objectbox` | **不推荐** | 许可无 copyleft 风险（Dart 与 C 库均 Apache-2.0，已验），但为 20 行引入 3.4 MB 原生 AAR + codegen + 向量/同步引擎，严重过度 |

> **这是本次调研唯一一处建议改动方案既定选型**（方案 §2/§4.1/§4.6/§4.8 共 7 行写的是 Drift）。**但它不构成重构**：`app/pubspec.yaml` 目前只有 `cupertino_icons` 与 `url_launcher`，**持久化代码一行都还没写**，换选型的成本是零。而且方向是**减少**依赖与构建复杂度，符合"不引入复杂依赖"的要求。详见 §10 第 3 条与 §10.1 第 5 项。

### 6.7 适老化 UI：不存在成熟的现成包

**先给结论，避免继续找**：pub.dev 搜 "senior" 命中的 `senior_design_system` / `senior_platform_authentication` 是巴西 Senior Sistemas 的 **HR 产品**，与适老无关；GitHub `flutter elderly accessibility` 前 6 个仓库 star 数 0–1，全是玩具项目。**这个方向没有可复用的成熟包，硬指标要靠 Flutter 内置 API 自己守。**

好消息是内置 API 已经够用，**运行时零新增依赖**：

### 6.9 一条生态预警

Material 正在从 Flutter SDK 解耦到独立的 `material_ui` / `cupertino_ui` 包（`pinput` CHANGELOG 7.0.0 引 flutter/flutter#184093，称 SDK 内置副本 "is frozen and scheduled for removal"）。`accessibility_tools` 3.0.0 已经依赖 `material_ui`。**选型时注意包的 Flutter SDK 下限**——本次已有多个包要求 ≥3.44/3.47，本机的 3.47.9 只是刚好够。

### 6.10 本节结论

**持久化只加 `sqflite`；适老化 UI 零运行时依赖**，用 `MediaQuery.withClampedTextScaling` + `Semantics` + 手写 `ThemeData` + 显式 72dp 约束；**仅加 `accessibility_tools` 作 `dev_dependency`**，让 72dp 与 1.3× 不溢出在开发期就被自动检查，而不是留到真机测试才发现。

**能减少的开发工作**：省掉整条 `build_runner` / codegen 链路与约 1500 行生成代码的维护；省掉自建无障碍检查工具；省掉自写坐标/主题/缩放适配的试错。**不能减少的**：地点 CRUD 界面、家属排序交互、POI 检索对接——这些没有任何现成包可复用，必须自己写。

### 7.1 `coordtransform_dart`：本次最该优先引入的包

GitHub：[ipcjs/coordtransform_dart](https://github.com/ipcjs/coordtransform_dart)，**BSD-3-Clause**，1.0.4（2024-06-13），纯 Dart，**运行时只依赖 `meta`**，238 行 + 119 行测试。

**为什么它重要**：ADR 0001 的 D3 要求"起点若来自 GPS，用 `/geoconv/v2/?model=2` 转 BD-09"，并在"后果"里写明 **D3 与 P0-2 绑在一起——如果 V1 不申请移动端 AK，起点转换就做不了**。这个包把该转换变成**纯本地计算**，直接解开这个绑定：不需要 AK、不需要网络往返、不需要代理。

**已做的核实**：

1. **Dart 3 兼容**：`sdk: '>=2.12.0 <4.0.0'`，本机 Dart 3.13.7 满足。
2. **算法是业界标准实现**：源码注释标明参考 `wandergis/coordtransform`。`wgs84ToBd09` = WGS84→GCJ02（闭式正向）→ GCJ02→BD09（闭式），**全程不涉及墨卡托反算**。
3. **独立交叉验算通过**：用独立 Python 实现同一算法，对公开测试点 `(118.3013077, 32.2719040)` 计算，与该包测试断言的期望值**吻合到 1e-9**：
   - GCJ02 → `(118.30667898630848, 32.26987097293956)`
   - BD09 → `(118.31309502519457, 32.276140342217744)`
4. **不重蹈 ADR 0001 事实 6 的覆辙**：那次失败是**自行实现 BD09MC→BD09LL 墨卡托反算**得到 `-9.68e33`。本包做的是**正向**转换，是不同的数学问题，那次失败不构成对本包的否证。

**必须知道的弱点（不影响本项目所需路径）**：

- `gcj02ToWgs84Raw` 用的是 `lng*2 - out[0]` 的**粗略近似**（:142-145），非迭代解，误差米级。**但 SeniorNav 只需要正向 WGS84→BD09**，反向路径用不到。
- `isInChina` 用粗矩形判断国境（:15-39）。合肥深处内陆，无边界风险；若将来出境需重新评估。
- 最后发布 2024-06-13，约 2.4 年未更新。但**算法是冻结的常量与公式**，不存在需要跟进的上游变化；238 行、零重依赖，风险极低。必要时可直接 vendoring。

**引入前必须做的一步（安全关键，不可省）**：坐标转换错了会让老人走错路口。按 ADR 0001 事实 1 的教训（不能靠 API 参数自证坐标系），**用同一批公共地标点，把本包的 `wgs84ToBd09` 输出与官方 `/geoconv/v2/?model=2` 的返回逐点比对**，确认偏差在米级以内再上线。这一步需要服务端 AK（已有），不需要真机。**在比对通过前，不要把它当作已验证。**

**判断：直接引入**（附上述交叉验证前置条件）。

**同类包全部不可用**（已核实 SDK 约束）：

| 包 | 最后发布 | 问题 |
|---|---|---|
| `coordtransform`（fluttercandies） | 2021-06-03 | `sdk <3.0.0`，**Dart 3 不兼容** |
| `gcoord_dart` | 2020-08-25 | `sdk <3.0.0`，仅 1 个版本 |
| `coord_convert` | 2021-03-12 | `sdk <3.0.0` |

### 7.2 `flutter_bmflocation`：功能对得上，但隐私上不能接受

官方百度定位插件，**Apache-2.0**（注意与 mapapi 系的 BSD-3 不同），3.8.5+1（2026-11-10，**两天前**，维护极活跃）。

**功能上非常契合**：

- `BMFLocationCoordType.bd09ll`（`lib/src/models/flutter_baidu_location_base_option.dart:8-17`）→ **直接返回 BD-09**，连 §7.1 的转换都不需要。
- **`singleLocation(Map arguments)`**（`lib/src/controller/bdmap_location_controller.dart:121`）→ 正好是方案 §4.7 要求的"前台取一次位置"，不是持续定位。
- `setApiKey` / `setAgreePrivacy` 齐备。

**但 AndroidManifest 是不可接受的**（`android/src/main/AndroidManifest.xml`，实测全文）：

```xml
<uses-permission android:name="android.permission.ACCESS_BACKGROUND_LOCATION" />
<uses-permission android:name="android.permission.READ_PHONE_STATE" />
<uses-permission android:name="android.permission.WRITE_EXTERNAL_STORAGE" />
<uses-permission android:name="android.permission.CHANGE_WIFI_STATE" />
<uses-permission android:name="android.permission.FOREGROUND_SERVICE" />
<uses-permission android:name="android.permission.WAKE_LOCK" />
<uses-permission android:name="com.android.launcher.permission.READ_SETTINGS" />
```

这些会**合并进最终 APK**：

- **`ACCESS_BACKGROUND_LOCATION` 直接违反方案 §6.2 验收第 9 条"无后台定位权限"**，也违反 §1.4"V1 不申请后台定位"与 §5.2 的最小化原则。
- `READ_PHONE_STATE` 读取设备标识，与"无用户画像"的隐私承诺冲突，且是应用商店审核的高敏感权限。
- 原生依赖 `BaiduMapSDK_Location_All:9.7.0` + `okhttp:4.12.0`，比 geolocator 重。
- 还需要 Android 端 AK——**给本来不需要 AK 的定位路径凭空增加一个 AK 依赖**，而 AK 正是当前 M0 的阻塞项。

可以用 `tools:node="remove"` 逐条移除，但那是额外的、易漏的、且无法保证 SDK 运行时不再索取的工作。

**判断：不推荐。** 改用 `geolocator`（WGS84）+ §7.1 的 `coordtransform_dart`（转 BD-09）：**零 AK、零百度原生依赖、无多余权限**，且解开 D3 的绑定。

## 9. 最值得优先复用的 3 个项目与具体接入位置

### 第 1 位：`coordtransform_dart` —— 直接引入，可立即开工

**接入位置**：新建 `app/lib/core/geo/coord_convert.dart` 作为薄封装，由未来的 `LocationProvider`（方案 §5.1）调用；`geolocator` 取到 WGS84 起点后转 BD-09，再交给 `RouteSummaryService`。

```
geolocator (WGS84)
   → app/lib/core/geo/coord_convert.dart   ← coordtransform_dart 在此
   → RouteSummaryService（全链路 BD-09，ADR 0001 D1）
```

**减少的工作**：省掉 `/geoconv/v2` 的 HTTP 调用、签名、错误处理与降级分支；**更重要的是解开 ADR 0001「后果」里 D3 与 P0-2 的绑定**——起点转换不再需要任何 AK。

**为什么排第一**：零风险（纯 Dart、零重依赖、BSD）、零阻塞（不需要 AK、不需要真机），且是本次唯一能**解开当前 M0 阻塞项**的引入。

**前置条件**：先与官方 geoconv `model=2` 做公共地标逐点比对（§7.1）。**这一步不能省。**

### 第 2 位：`sqflite` —— 直接引入，替换方案既定的 Drift

**接入位置**：`app/lib/data/`（方案 §4.8）的 `PlaceRepository` 实现（方案 §5.1 已定义该接口）。新建 `app/lib/data/place_dao.dart`，用 `openDatabase(version: 1, onCreate: …, onUpgrade: …)` 建 §4.6 的 16 列表；`meta` 表存 PIN 与 `schemaVersion` 之外的单值设置。**接口与分层位置不变，只换内部实现。**

```
PlaceRepository（方案 §5.1 接口，不变）
   → app/lib/data/place_dao.dart   ← sqflite 在此
   → Android 系统 SQLite（零原生依赖、APK 不增大）
```

**减少的工作**（已量化，§6.3–§6.5）：

- 省掉约 **1200–1800 行生成代码**及其维护——官方 2 列示例就生成 367 行。
- 省掉整条 `build_runner` / `drift_dev` 链路、`build.yaml`、`drift_schemas/` 快照、`database.steps.dart`，以及 `analyzer >=13 <15` 参与的全局依赖求解。
- 省掉**构建期从 GitHub Releases 下载 `.so`** 这个前置条件——在本机的 Clash TUN + CGNAT 多出口环境下，这是实打实的失败点。
- 手写成本约 200 行，且迁移回调自带事务（`sqlite_api.dart:506-507`），V1→V2 加列不需要额外工具。

**为什么排第二而不是第三**：它和第 1 位一样**无条件、零阻塞、可立即开工**，而第 3 位要等 D1 决策。BSD-2、3020 stars、昨天还有提交，是本次调研中维护最活跃的包。

**配套**：`accessibility_tools` 作 `dev_dependency` 一同引入（§6.8），把 72dp 与 1.35× 不溢出变成开发期自动检查，而不是留到真机测试。

### 第 3 位：`flutter_baidu_mapapi_search` 的 POI / Suggestion 检索 —— D1 选 B 时直接引入

**接入位置**：`app/lib/data/`（方案 §4.8 的 data 层）新建 `place_search_service.dart`，供家属设置的地点录入页（方案 §3.6"搜索 → 选择 → 地图确认入口"）调用；产出的 `naviLocation` 与门 uid 写入 `PlaceRepository` 的 `naviLatitude`/`naviLongitude`/`poiUid` 字段（ADR 0001 D2 要求新增的字段）。

**减少的工作**：地点录入的整个数据侧——输入提示、POI 详情、精确坐标、出入口子点，全部现成。这是 V1 尚未开工的最大一块。

**条件与代价**：仅在 D1 选 B（Android SDK）时成立。若 D1 选 A，POI 应同样走无服务器代理的 `/place/search`（方案 §4.6 已写明），插件不引入。**注意混合架构会需要两个 AK**（§3.4）。

**明确边界**：**只用 POI/Suggestion，不用它的路线检索**（§3.2）。路线继续走现有 `baidu_route_parser.dart`（A 路）或自建薄通道（B 路，§3.7）。

## 10. 现有技术架构是否需要调整

**结论：架构不需要调整；有一处选型微调（Drift → sqflite），不构成重构。** 五条理由：

1. **分层被验证是对的。** 方案 §5.1 要求"UI 不感知数据源"，`route_summary.dart` 的文件头也写明"D1 切换数据源时本文件不需要改动"。本次三个候选数据源方案（官方插件、Trufi/OTP、自建通道）全都能落到同一个 `RouteSummary` 上——**这层抽象恰好挡住了它们各自的缺陷**。若当初把百度字段直接铺进 UI，现在就得跟着插件的字段缺口一起返工。

2. **`NavigationLauncher` 抽象成 provider 的决定（评审意见 P1-9）同样被验证。** map_launcher 的百度实现不合格，但因为它只是 provider 的一个候选实现，否决它不影响架构。

3. **技术选型只有一处微调：Drift → sqflite（§6.6）。** Flutter + Riverpod + url_launcher 全部保留，`PlaceRepository` 的接口与分层位置不变——变的只是它内部用什么写 SQL。三点让它不算重构：
   - **代码还没写**：`app/pubspec.yaml` 目前只有 `cupertino_icons` 与 `url_launcher`，持久化零行代码，换选型成本为零；
   - **方向是减依赖**：去掉 codegen、`build_runner`、analyzer 版本锁与构建期下载 `.so`，正好符合"不引入复杂依赖"的要求；
   - **数据模型不动**：方案 §4.6 的 16 列、软删除墓碑、`rev` 冲突解决、`schemaVersion` 全部原样落到 sqflite 的建表语句与 `onUpgrade` 里。

   `url_launcher` 继续用——`baidu_uri.dart` 构造 URI、`url_launcher` 负责调起，职责清晰，且已声明 `<queries>`。**适老化 UI 不引入任何运行时包**（§6.7），因此也不影响架构。

4. **不引入后端的原则守住了。** Trufi 的 OTP 依赖、`flutter_bmflocation` 的 AK 依赖，都是把 V1 往"需要外部服务"的方向推。方案 §1.4/§4.2 的边界是对的。**sqflite 用系统 SQLite，同样不引入任何外部服务或构建期网络依赖。**

5. **需要新增的都是薄封装，不是改结构**：`app/lib/core/geo/coord_convert.dart`（§9 第 1 位）、`PlaceRepository` 的 sqflite 实现（约 200 行）、首页外层的 `MediaQuery.withClampedTextScaling` 一行。这些都是填空。

### 10.2 对 D1 的影响

**本次调研不关闭 D1**，与 ADR 0003 的立场一致——没有 AK、没有真机，运行时行为一律未验证。

但它改变了 D1 的权衡：

- **B 路的实现方式有了明确优选**：若选 B，**自建薄通道优于官方检索插件**（§3.7）。ADR 0003 已完成最难的静态工作，剩余 Kotlin 量很小，且能保住 `direct_text` 与 `stop_info`。
- **A 路的相对优势增强**：A 路字段语义已实测、解析器已写好并被测试锁住，且**不需要 Android AK**——而 AK 正是当前阻塞项。
- **B 路新增一条此前未计的成本**：官方插件不可直接用于路线，所以 B 路要么自建通道，要么维护 fork。ADR 0003 §6"B 路在静态层面没有可见阻塞项"的结论**对原生 AAR 仍成立**，但**对"用官方 Flutter 插件走 B 路"这条捷径不成立**。
