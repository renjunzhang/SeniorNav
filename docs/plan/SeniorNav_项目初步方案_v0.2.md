# SeniorNav｜老年人极简出行决策助手

**项目方案 v0.2**  
文档日期：2026-11-12　｜　阶段：交互设计冻结 / 技术待验证  
开发目标：先交付 Android V1（本地地点数据 + 百度路线摘要），再评估 V2 家属远程配置。

> **一句话定位**：家属把常去地点设好，老人点一下，先用大字看懂公交/步行方案，再按需打开百度地图导航。

---

## 1. 定位与边界

### 1.1 要解决的问题

老人出门时真正困难的部分，往往不是"不会用地图"，而是：

- 要先搜索目的地，输入法、同名地点、选错入口都可能出错；
- 地图 App 的路线页信息密集，公交方案要自己比较、选线路；
- 不知道坐哪路车、往哪个方向、在哪站下、下车后往哪走。

SeniorNav 把这三步拆开：**家属预设地点 → 老人点一下 → 先看摘要，再决定是否导航。**

### 1.2 产品定义

SeniorNav 不是地图软件，也不是导航软件，而是一个**极简出行决策助手**：

- 目的地由家属预先配置，老人不需要搜索；
- 路线数据来自百度地图，SeniorNav 只负责"选一条、翻译成大字短句"；
- 真正的转向级导航仍交给百度地图客户端。

### 1.3 核心原则

1. **五个入口，零搜索**：首页只放五个大按钮，纵向排列，不滚动。
2. **先摘要，后导航**：点地点后先展示可读的公交/步行方案，而不是立即跳转。
3. **路线数据必须来自百度**：不用 AI 编造线路、站点、时间；摘要只做解析和改写。
4. **规则化摘要**：固定规则 + 固定文案，可测试、可复现。
5. **老人端极简，家属端承担配置**：老人首页不出现管理、搜索、设置。
6. **渐进交付**：V1 只做"地点 + 摘要 + 按需导航"；V2 再做家属远程配置。

### 1.4 非目标（本期不做）

- SOS、防走失、电子围栏、全天候位置共享；
- 实时公交到站、上下车提醒、全程语音导航；
- 自研地图、路径规划、POI 数据库；
- AI 迷路识别、大模型生成路线；
- iOS 上线、账号体系（V1）；
- 替代 110/120 等紧急救援。

> 位置共享是否进入 V2，另行评估；V1 不申请后台定位。

### 1.5 部署形态假设

**单家庭自用，家属侧载安装 APK，不上架应用商店。**

这一条假设决定 V2 的成本量级，必须先写死（评审意见 P0-5）：

- 侧载自用可避开应用商店审核、App 备案、隐私政策公示等大部分流程；代价是换机/丢失时的恢复要靠自己（见 §3.6 的导出/导入）。
- 一旦要上架或公开分发，会引入 App 备案、软著、隐私政策与权限清单、域名 ICP 备案；V2 若在云端存位置，属于敏感个人信息，合规义务显著上升。
- 因此：本期不承诺上架；如未来要上架，另立专项，不在 V1/V2 里默认承担。

侧载还带来一个必须解决的运维问题——**APK 怎么升级、出问题怎么取日志**（评审意见 P1-5）。V1 无后端，这两件事不会自动发生，见 §10 D8。

## 3. V1 交互设计

### 3.1 首页：五个按钮，不滚动

首页只有五个纵向大按钮，顺序固定，不随使用频率变化：

| 顺序 | 按钮 | 默认内容 | 说明 |
|---|---|---|---|
| 1 | 回家 | 家的地址 | 家属确认，不可删除 |
| 2 | 去孙女家 | 示例，可改名/改地点 | 家属可替换为其他常去地点 |
| 3 | 医院 | 示例，可改名/改地点 | 家属可替换为公园、菜市场等 |
| 4 | 超市 | 示例，可改名/改地点 | 家属可替换 |
| 5 | 更多地点 | 其余已配置地点 | 进入列表页，不在首页展开 |

布局与视觉约束：

- 纵向排列，**整个首页不需要滚动**；目标机型 5.5–6.7 英寸、系统字体 1.3× 下仍完整显示。
- 按钮高度不低于 72dp；文字 24sp 左右；图标 + 文字，不使用 emoji（避免不同机型渲染差异）。
- 顺序固定，不按频率重排；老人依赖位置记忆。
- 首页不出现搜索框、设置、管理、账号入口。
- 家属入口隐藏在标题区域（长按 2 秒 + PIN，或连点 3 次 + PIN），只防误触，不作为安全认证。
- "联系家人"不占首页第六个按钮，放在路线摘要页和异常页的底部（可选），保留电话兜底。

### 3.2 点击一个地点之后

1. 前台获取一次当前位置（不后台、不上传、不落库）。
2. 查询公交与步行方案。实测两者串行合计 0.42–0.80 秒（ADR 0002 §2.1），并行也来得及；但路线规划服务个人认证只有 **3 并发**，客户端超时不会释放服务端并发槽，因此 §4.3 的补救查询必须等前两次返回后再发，超时后不自动重发（ADR 0002 A8）。
3. 按规则选出一条方案，生成大字摘要。
4. 展示摘要页：默认选中推荐方式，老人可切换公交/步行。
5. 老人点击"打开地图导航"，调起百度地图。

若定位失败、网络失败或路线查询失败：仍然展示"打开百度地图"按钮，由百度地图自行定位并规划，不出现空白页。

### 3.3 路线摘要页

摘要页只做一件事：让老人**在出发前看懂**。

| 区域 | 内容 |
|---|---|
| 顶部 | "去孙女家"（目的地名称，大字） |
| 方式切换 | 两个大按钮："坐公交" / "走路"；不是小 tab |
| 推荐标识 | 推荐的方式加"推荐"标签；默认选中 |
| 公交摘要 | 总时长、步行到站、线路名 + 方向、坐几站、下车站、换乘、下车步行 |
| 步行摘要 | 总距离、总时长、是否需要过街提示（来自百度 steps） |
| 底部固定 | "打开地图导航"大按钮；次要操作"重新查询" |
| 页脚 | 查询时间；"路线以百度地图为准" |

公交摘要示例（正式运行由百度 API 返回，不在代码中写死）：

```text
回家 · 坐公交
约 35 分钟（含步行）

① 步行约 200 米 → XX 站
② 坐 XX 路（开往 XX 方向），6 站
③ 在 XX 站下车，步行约 300 米

不用换车
```

文案规则：

- 用"约/预计"，不写"实时"；百度没有实时到站就不暗示。
- 先写"不用换车 / 要换 1 次车"，这是老人最关心的信息。（本节上面的示例把它排在步骤之后，与本条矛盾；实现按本条执行——紧跟总时长行，示例视为排版示意。）
- 非运营时段必须降级提示：百度**不校验首末班**，凌晨 2 点查询照样返回首班 06:12 的地铁方案。摘要要用 `first_time`/`last_time` 与当前时间比对，命中就加一行"XX线 首班 06:12，现在可能还没发车"（ADR 0002 A7）。
- 步行过街提示只能靠在 `instructions` 文本里匹配关键词（天桥/过马路/斑马线等），百度没有结构化字段，属尽力而为。命中数为 0 时**不要**写"沿途不需要过马路"——没提到不等于没有。
- `instructions` 含 HTML 标签（`走20米,<b>左转</b>`），展示前必须去标签。
- 站数直接写"坐 6 站"。`stop_num` 的语义已实测确认：等于**站间数**（不含上车站、含下车站），恒等于 `stop_info` 长度 + 1，5 个乘车段样本全部吻合，因此不需要降级成"6 站左右"（ADR 0002 A3）。
- 线路名、站名不截断；长名称换行显示，不缩小字号。实测站名带出入口字母（`合肥南站(C口)`、`大蜀山站(C口)`），排版要按这个长度设计。
- **换乘步行必须可见，并进换乘行**：写成「步行约 500 米，换 320路（开往 …），10 站，XX下车」，不单独占一行——4 行预算下单独一行会把「换哪路车」挤掉。实测 `metro_direct` 方案 2 总步行 941 米，其中 495 米是换乘步行；修复前文案只印 60 + 390 米，老人看不到下车后还要走半公里。同站换乘（`boardWalkM == 0`）不写「步行约 0 米」。
- 摘要最多 6 行：总时长 1 行 + 换车提示 1 行 + 步骤最多 4 行。超过 4 段就截断，末行写"之后的换乘请打开百度地图查看"；更细的步骤交给百度地图。
- 按本节规则、用真实录制的百度响应渲染出的三张样张见 `docs/m0/纸面摘要样张.md`，即 M0 任务 3 的朗读测试材料。样张由 `app/tool/render_paper_summary.dart` 生成，不手抄。

### 3.4 自动推荐公交还是步行

不能只看直线距离。用**实际路线结果**比较：

| 条件 | 推荐 |
|---|---|
| 步行距离 ≤ 1.0 km 且步行时长 ≤ 20 分钟 | 走路 |
| 公交存在，且公交总时长比步行少 5 分钟以上 | 坐公交 |
| 步行 ≤ 2.0 km，且步行时长不超过公交 10 分钟 | 走路 |
| 其他有公交方案的情况 | 坐公交 |
| 没有公交方案 | 走路（并提示距离） |
| 步行 > 3 km 且没有公交方案 | 提示"距离较远"，优先打开百度地图 |

规则细节：

- 表格自上而下匹配，**第一条命中即返回**，不是打分求和。
- 用时、步行距离、换乘次数都来自路线结果，不用直线距离估算。
- "公交总时长比步行少 5 分钟以上"取**严格大于**：正好快 5 分钟时交给第 3 条规则判断，否则第 3 条（步行 2 公里内且不慢 10 分钟以上）在边界上永远轮不到，老人会被多带去换乘。
- "没有公交方案"的判据是 `status == 0 且 routes 为空`，不是 `status != 0`。实测 95 米的起终点就返回这种形状，那是成功响应；当成接口失败会让老人看到"暂时查不到路线"，而正确答案是"走路"（ADR 0002 A6）。
- 两种方式都展示，推荐只决定默认选中，不隐藏另一种。
- 不记忆"上次选择"，避免老人下次被带到不熟悉的模式；每次按路线重新推荐。
- 若公交方案需要换乘 **1 次以上**（原为 2 次以上，按 ADR 0002 A5 收紧），标注"要换 N 次车"，并用"少换乘"策略重查一次再比较。这是一次额外的网络请求，必须等前两次返回后再发（并发上限 3）。

### 3.5 更多地点

- 展示第 5 个以后的所有地点，纵向大行，每行一个地点。
- 只做"选择目的地"，不做搜索、编辑、删除。
- 返回按钮大而明显；列表可滚动，首页不滚动。
- 地点过多时，由家属在设置里排序，老人端不排序。排序只作用于本列表；首页四个按钮的位置由 `slot` 固定，家属改动后也不自动重排（§3.1：老人依赖位置记忆）。列表顺序存 `sortOrder`，见 §4.6。

### 3.6 家属设置（V1 在老人手机上）

- 入口：标题区长按 2 秒 + PIN；或连点 3 次 + PIN。
- 可修改：家的地址；3 个首页地点的名称、图标、地址；更多地点列表；PIN。
- 地点录入必须走"搜索 → 选择 → 地图确认入口"三步，不能只存一个名称：
  - 搜索百度 POI/输入提示；
  - 保存名称、地址、城市、经纬度、坐标系、POI UID；
  - 在地图上确认一次入口（医院尤其重要）。
- 保存后老人首页立即生效；不重启 App。
- V1 不做账号、不做云同步；换机/清数据需要重新配置（V1.1 可加导出/导入）。

### 3.7 失败与异常

| 情况 | 老人看到的 |
|---|---|
| 定位权限被拒 | "无法获取位置，请让家人打开定位" + "打开百度地图" |
| 定位关闭/信号弱 | "位置不确定" + 重试 + "打开百度地图" |
| 无网络 | "网络不好，先打开百度地图" |
| 路线接口失败/配额不足 | "暂时查不到路线" + "打开百度地图" |
| 接口返回成功但结构变了 | 同上。必须捕获，不能白屏——百度升级接口时会走到这条路径 |
| 当前不在运营时段 | 摘要照给，但加一行"XX线 首班 06:12，现在可能还没发车" |
| 百度地图未安装 | 安装指引 + 网页版路线链接 |
| 百度地图版本过旧 | 同上，走网页回退。**`walknavi` 需客户端 ≥ 8.8，低于 8.6.9 完全不支持步行导航**（`flutter_baidu_mapapi_utils` 的 `bmf_open_navi_options.dart:9-22` 版本注释，ADR 0004 事实 6）。老人手机上的百度地图很可能长期未更新，调起会静默失败，因此不能把「已安装」当成「能导航」。M0 任务 4 必须记录客户端版本号 |
| 没有公交方案 | 展示步行方案；步行也太远则提示 |
| 查询超过 5 秒 | 显示"仍在查询…" + 可直接打开百度地图 |

所有失败路径都必须保留"打开百度地图"这一条出路；摘要失败不能导致无法出行。

### 3.8 适老化与无障碍

- 正文不小于 18sp，按钮文字 22–24sp；对比度 ≥ 4.5:1。
- 触控目标 ≥ 72dp；按钮之间留足间距，防误触。
- 不依赖颜色传达状态；推荐标签同时有文字。
- 支持系统字体 1.3× 和 2×；1.3× 下首页不滚动，2× 下允许首页和摘要页滚动，但按钮与文字不被截断。
- TalkBack：按钮读"回家，按钮"；摘要按步骤朗读。
- 强制浅色高对比主题；不跟随系统深色模式（户外强光下更清楚）。
- 不使用 emoji 作为唯一图标；使用矢量图标 + 文字。

## 4. 技术方案

### 4.1 总体结构

```text
Flutter Android
  UI / 状态（首页、摘要、更多、家属设置）
        │
  RouteSummaryService ──→ 百度路线数据（二选一）
        │                   A. 无服务器函数代理 Web API
        │                   B. 百度 Android SDK 本地检索
        │
  PlaceRepository（sqflite/SQLite）     LocationProvider（前台一次定位）
        │
  NavigationLauncher ──→ 百度地图客户端（walknavi / direction）
```

### 4.2 路线数据来源：M0 先做技术选择

百度 Web API 的公交/步行接口能返回结构化路线；但官方文档明确这类服务**需要使用服务端 AK 调用**。因此有两条可行路线：

| 方案 | 做法 | 优点 | 代价 |
|---|---|---|---|
| A. Web API + 无服务器函数 | 阿里云 FC / 腾讯云 SCF / Cloudflare Worker 代理 `direction/v2/*` | 字段最全；逻辑集中；将来 H5 可复用 | 多一个服务；AK/SN、配额、域名/HTTPS、可用性 |
| B. Android SDK | Flutter 通过平台通道调用百度 SDK 的路线检索 | 无后端；AK 绑定包名 + SHA1 | APK 变大；SDK 隐私合规；需验证能否不依赖地图视图、字段是否够用 |

**决策规则**：M0 用 1 天做 B 的 spike。若 SDK 能返回公交线路、方向、上下车站、站数、换乘、步行距离，且延迟可接受，则 V1 选 B（无后端）；否则选 A，并且只做**无状态代理**。

无论 A/B，App 侧都通过 `RouteSummaryService` 接口访问，UI 不感知来源，便于后续切换。

若选 A，代理服务的最小要求：

- 只暴露一个只读接口，例如 `POST /route/summary`；不存路线、不存位置。
- App 携带每设备令牌或 HMAC；服务端限流、校验坐标范围与 mode 白名单，避免成为开放代理。
- AK 放服务端环境变量；开启 IP 白名单；如启用 SN 校验，`sn` 在服务端计算。
- 超时 3 秒；失败/配额不足返回明确错误码；App 回退到百度地图。
- 不记录含坐标的访问日志；如需排障，只记录脱敏后的耗时/错误码。

### 4.3 百度路线接口契约

| 接口 | 用途 | 关键参数 |
|---|---|---|
| `direction/v2/transit` | 公交/地铁方案 | `origin`、`destination`、`coord_type`、`ak`、`sn`、`tactics_incity`、`destination_uid` |
| `direction/v2/walking` | 步行方案 | `origin`、`destination`、`coord_type`、`ak`、`sn`、`destination_uid` |
| 百度地图 URI | 打开客户端导航 | `walknavi` 步行导航；`direction?mode=transit` 公交路线页 |

已核验的要点（2026-11-12 实测，证据见 `docs/adr/0002-路线数据源WebAPI实测.md`）：

- `coord_type` 支持 `bd09ll`、`bd09mc`、`gcj02`、`wgs84`，默认 `bd09ll`。
- `tactics_incity`：0 推荐、1 少换乘、2 少步行、3 不坐地铁、4 时间短、5 地铁优先。逐个取值实测确认无误。
- **公交响应的实际结构**（此前描述的层级不对，照旧写法实现会直接抛类型错误）：

```text
result.routes[]                # duration / distance / price / price_detail / arrive_time / steps
  └─ steps[]                   # ← 列表的列表，不是对象数组
       └─ [segment]            # trans_type / distance / duration / instructions / path
                               # start_location / end_location / traffic_condition
            └─ vehicle_info    # ← 这一层只有 {type, detail} 两个键
                 └─ detail     # name / type / bus_type / direct_text / stop_num / stop_info[]
                               # on_station / off_station（纯字符串，不是对象）
                               # first_time / last_time / line_id / line_color
                               # start_info{} / end_info{} / shuttle_time_table[]
```

- 有两个 `type`，含义完全不同，不能混用：`vehicle_info.type` 是**分段类型**（3 = 乘车段，5 = 步行段或同站换乘标记，此时 `detail` 为 null）；`vehicle_info.detail.type` 才是**线路类型**（0 普通公交、1 地铁/轻轨）。判定乘车段以 `detail` 是否为 null 为准，`trans_type` 作辅助（0 步行、-1 乘车、3 同站换乘）。
- 步行响应的 `routes[].steps` 是**扁平对象数组**，与公交的嵌套形状不同；且 walking 用 camelCase（`originLocation`），transit 用 snake_case，解析层不能复用同一套字段名。
- `departure_time` 只接受 `HH:mm`（最长 11 字符）。传 Unix 时间戳返回 `status=2 参数有误`，传 `YYYY-MM-DD HH:mm:ss` 返回"最大长度是11"。本期默认不传。
- `destination_uid` 带与不带，返回方案与耗时完全一致，未观测到差异；不能据此断定被忽略，需换一个入口复杂的 POI（如医院）复测。

接口调用策略：

- 默认 `tactics_incity=0`（推荐）；**若换乘 ≥ 1**，再用 `1`（少换乘）查一次并比较。（此前定为默认 2、补救条件 >1，实测是净损失，见下方说明。）
- 公交与步行两次请求可并行，结果缓存 2–5 分钟（仅内存）；但补救查询必须等前两次返回后再发。
- 路线规划服务个人认证只有 **3 并发**，客户端超时不释放服务端并发槽。超时后不自动重发；若走 A 路，代理层必须限流排队（ADR 0002 A8）。
- 家庭可在设置里选择偏好："少走路"（默认）或"少换车"；默认不改老人端。
- `stop_num` 语义已确认为站间数，`end_name` 已确认为下车站（不是终点站），两者都不再是待验证项。

> **为什么把默认策略从 2 改成 0**：大蜀山森林公园→安徽省立医院，`tactics_incity=2`（少步行）给 87.6 分钟 / 1 次换乘 / 步行 862 米，`0`（推荐）给 39.9 分钟 / 0 次换乘 / 步行 1302 米。少步行省下 440 米，代价是多花 47.7 分钟、多换一次车——这与 §4.4 自己的排序（先比换乘）和 §3.3 的"先写不用换车"直接矛盾。而旧的补救条件"换乘 > 1"恰好不触发（换乘数是 1），这条 87.6 分钟的方案会原样展示给老人。最终取值待 §6.3 的 12 类场景比对后确认。

> **两套策略枚举不能共用常量**：百度地图 URI API 的 `sy` 参数是另一套编号——0 推荐、2 少换乘、3 少步行、4 不坐地铁、5 时间短、6 地铁优先（没有 1）。同一个数字在两个接口里含义相反（`tactics_incity=2` 是少步行，`sy=2` 是少换乘）。V1 同时用两个接口，共用常量会导致摘要按少步行算、打开的地图按少换乘算，而摘要页还写着"以百度地图为准"（ADR 0002 A4）。

### 4.4 摘要生成规则

`RouteSummary` 统一结构（字段映射按实测修正，实现在 `app/lib/route_summary.dart`）：

| 字段 | 来源 | 说明 |
|---|---|---|
| `mode` | — | transit / walking |
| `durationSec` / `distanceM` | `routes[].duration` / `distance` | 总时长、总距离 |
| `walkM` | 各 `trans_type == 0` **或 `4`** 段的 `distance` 求和 | 总步行距离。0=普通步行，4=换乘步行（漏掉会让"步行到上车站"整行消失）；3=同站换乘标记，距离恒为 1 米，计入会虚高 |
| `legs[]` | `steps` 的**每一组**取第一条 `vehicle_info.detail` 非空的段 | **一段乘车一个元素**。同组里的多条车辆段是"这一段可任选其一"的备选线路，不是连续乘车，全建 leg 会把 1 次换乘算成 3 次（ADR 0002 §2.11） |
| `legs[].lineName` | `detail.name` | 线路名，可空 |
| `legs[].lineType` | `detail.type` | 0 公交 / 1 地铁，可空 |
| `legs[].direction` | `detail.direct_text` | **开往方向。禁用 `end_info.end_name`——那是下车站** |
| `legs[].boardStop` / `alightStop` | `detail.on_station` / `off_station` | 纯字符串 |
| `legs[].stopCount` | `detail.stop_num` | 站间数，直接用于"坐 N 站" |
| `legs[].firstTime` / `lastTime` | `detail.first_time` / `last_time` | 用于运营时段校验 |
| `legs[].boardWalkM` | 该段之前的步行距离 | 首段渲染「① 步行约 710 米 → XX站」；后续段并进换乘行「步行约 500 米，换 …」，不单独占行（§3.3） |
| `transfers` | 派生：`legs.length − 1` | 换乘次数。做成派生属性，避免两处各算一遍 |
| `crossingCount` | walking `steps[].instructions` 关键词命中数 | 过街提示，尽力而为 |
| `arriveTime` | `routes[].arrive_time` | 仅展示，不参与推荐 |
| `fetchedAt` | **调用方给的查询时刻** | 不能用 `arrive_time`，否则 5 分钟过期判断永远不触发 |

> **本节原先把 `lineName`/`direction`/`boardStop`/`alightStop`/`stopCount` 列成 RouteSummary 的扁平字段，装不下换乘线路**：1 次换乘有 2 段乘车，每段各有自己的线路名、方向、上下车站和站数。已改为 `legs[]` 列表。

规则：

- 只选 1 条推荐方案，不展示方案列表。
- 先比较换乘次数，再比较步行距离，最后比较时长；推荐结果与自动推荐规则（3.4）一致。
- **选路要重排，不能直接用百度返回的第一条**：实测 `tactics_incity=2` 的响应里，0 换乘的轨道交通 2 号线被排在第 5 位，87.6 分钟/1 换乘的方案排在第 1 位。
- 排序前先过滤明显绕路的方案：**时长 ≤ 最快方案 + 10 分钟，且里程 ≤ 最短方案 × 2**；过滤后为空则只按时长过滤，绝不抛错。这是"换乘多、步行远的方案直接淘汰"的落地口径——只按换乘排序会选中"0 换乘但绕远"的方案。**10 分钟 / 2 倍是 M0 暂定阈值**，待 §6.3 的 12 类场景跑完后复核（ADR 0002 A11）。
- 文案由固定模板生成，禁止大模型改写；每个字段缺失时要有降级文案，不能编造（方向缺失就整段省略括号，不写"开往 未知 方向"）。
- 必须校验 `first_time`/`last_time`；非运营时段加告警行，不能照印（ADR 0002 A7）。
- 摘要页显示"查询时间"；超过 5 分钟提示"重新查询"。
- 开发期用真实 JSON 录制 fixture 做单元测试；演示数据只允许出现在 debug 包。fixture 在 `app/test/fixtures/`，测试在 `app/test/baidu_route_parser_test.dart`、`app/test/route_summary_test.dart` 与 `app/test/baidu_uri_test.dart`（共 76 个用例）。
- Release 包增加一条测试：不得包含演示线路常量。
- 票价（`price`/`price_detail`）实测存在但本结构未包含；对老人有价值，是否加入待评估。

### 4.5 导航调起

- 步行："打开地图导航"优先用 `baidumap://map/walknavi`，直接进入步行导航；失败再退回 `direction?mode=walking` 的路线页。
- 公交：用 `baidumap://map/direction?mode=transit` 打开百度地图路线页；摘要只是预习，百度地图可能给出不同方案，文案标"以百度地图为准"。
- 百度地图未安装：打开网页版路线页（不是搜索页），并给出安装指引。
- 所有调起失败都返回摘要页，不出现空白页。

### 4.6 地点与数据

V1 数据模型（本地 sqflite，手写 schema 与迁移，不用代码生成——见 ADR 0005）：

| 字段 | 说明 |
|---|---|
| `id` | UUID |
| `slot` | 1 家、2–4 首页地点、0 更多地点 |
| `label` | 老人端显示名称（如"去孙女家"） |
| `icon` | 图标标识 |
| `name` / `address` / `city` | POI 名称、完整地址、城市 |
| `latitude` / `longitude` / `coordSystem` | 坐标与坐标系（BD-09 / GCJ-02 / WGS84） |
| `poiUid` | 百度 POI UID，用于提升终点入口准确性 |
| `updatedAt` | 更新时间 |
| `rev` | 预留 V2 同步版本 |
| `sortOrder` | "更多地点"列表的显示顺序（§3.5 要求家属可排序，没有这个字段就排不了） |
| `verifiedAt` | 家属在地图上确认过入口的时刻；为 null 表示尚未核对（§6.2 验收要求"位置核对"，没有这个字段就无法区分核对过和没核对过的地点） |
| `deletedAt` | 软删除墓碑。V2 同步必须能传播删除，否则家属删掉的地点会在老人端复活 |

表级字段：`schemaVersion`（本地库结构版本，用 SQLite 的 `PRAGMA user_version`，即 `openDatabase(version: n)`，不是每条地点一行）。

- `slot` 只管首页四个固定位置，不能替代 `sortOrder`：slot 只有 1／2–4／0 三档，撑不起"更多地点"的任意排序。
- 保留 `rev` 就必须同时保留 `deletedAt`。冲突解决用 `rev`（服务端权威）而不是 `updatedAt`——时钟漂移会让"最后写入"不可靠（评审意见 P1-3）。
- 墓碑保留期待 V2 定；V1 只写 `deletedAt`，不做清理。

- 不保存路线；路线摘要只在内存中，带 `fetchedAt`。
- 地点录入走百度 POI 检索；若走 A 方案，由代理提供 `/place/search`；若走 B，用 SDK 的 POI 检索。
- 坐标统一存 BD-09；GPS 起点按需转换，避免同一请求混用坐标系。

### 4.7 定位

- 只在前台、点击目的地时取一次位置；不后台、不持续、不上传。
- 权限说明由家属在配置时完成；老人端只出现系统弹窗。
- 精度差于 100 米时提示"位置可能不准"，并允许重试或直接打开百度地图。
- 拒绝定位时仍可打开百度地图（由百度自行定位），只是没有摘要。

### 4.8 目录与技术选型

```text
app/lib/
├── features/
│   ├── home/          # 五个按钮
│   ├── route/         # 摘要页、自动推荐
│   ├── places/        # 更多地点、家属设置
│   └── settings/
├── core/              # 主题、异常、权限、平台适配
└── data/              # sqflite、Repository、摘要服务
```

| 层次 | 选型 | 说明 |
|---|---|---|
| 移动端 | Flutter + Dart | 只交付 Android，保留 iOS 适配层 |
| 状态管理 | Riverpod | 简单、可测试 |
| 本地存储 | sqflite + 系统 SQLite | 地点与设置；不做路线持久化。不用 Drift：单表约 20 行、无 join，代码生成与构建期下载 `.so` 的收益为零（ADR 0005） |
| 定位 | Android 前台定位（geolocator 或平台通道） | 一次定位 |
| 路线 | 百度 Web API 代理 或 Android SDK | M0 决策 |
| 导航调起 | url_launcher + 百度 URI | 步行 walknavi；公交 direction |
| 服务端（可选） | 无服务器函数 | 仅代理，无数据库 |

本地数据的泄露面（评审意见 P1-1）：

- Flutter 模板默认 `allowBackup=true`，SQLite 里的家庭地址会被系统云备份带走。必须设 `android:allowBackup="false"`，或用 backup rules 排除 sqflite 数据库文件。当前工程已设（`app/android/app/src/main/AndroidManifest.xml`）。
- 家属入口的 PIN **只防误触，不防取证**。威胁模型里要写明这一点，不能让人误以为地点数据被加密保护了。
- 侧载分发意味着没有商店的自动升级通道，版本号可见与诊断导出见 §10 D8。

## 5. 接口与隐私

### 5.1 关键接口

- `LocationProvider`：请求权限、取一次位置、返回精度与时间。
- `RouteSummaryService`：输入起点/终点/模式，返回 `RouteSummary`；内部处理 A/B 数据源、缓存、超时、错误码。A 路的解析实现在 `app/lib/baidu_route_parser.dart`，D1 若改选 SDK 只换这一层，`route_summary.dart` 的模型与文案规则不动。
- `NavigationLauncher`：按模式调起地图客户端；处理未安装、失败回退。**抽象成 provider 而不是直接写百度**（评审意见 P1-9）：老人手机不一定装百度地图，华为/小米机型可能只预装高德。V1 只实现百度 provider，但接口按多 provider 设计，并在 M0 记录目标机实际装了哪些地图 App。
- `PlaceRepository`：本地地点增删改查；V2 替换为本地优先 + 同步。

### 5.2 隐私

- 位置属于敏感个人信息；V1 只在前台使用，不后台采集、不上传服务器（A 方案的代理只透传查询，不落库）。
- 代理服务不记录坐标；如必须记录，做脱敏并限制保留时间。
- 百度地图数据展示遵守其署名与使用条款；摘要页标注"数据来源：百度地图"。
- V1 无账号、无用户画像、无广告 SDK；如后续加统计，需单独评估。

### 6.2 V1 验收标准

1. 首页固定五个按钮，目标机型 + 系统字体 1.3× 下**不需要滚动**；按钮高度 ≥ 72dp。
2. 家 + 3 个首页地点可由家属修改并持久化；重启 App 后保留。
3. 点击地点后 3 秒内（p95）出现摘要；线路名、方向、上/下车站、站数、步行距离、总时长与百度地图对比在可接受误差内。
4. 自动推荐使用实际路线数据；500 米、5 公里两类场景推荐正确；老人可手动切换。
5. "打开地图导航"能到正确目的地；步行优先直接进步行导航；百度地图未安装时有网页回退。
6. 无网络、定位拒绝、接口失败、无公交方案、超时五种情况均有明确提示和"打开百度地图"出路。
7. Release 包不含演示线路数据；摘要页显示查询时间与"以百度地图为准"。
8. 老人（实际使用者）在陪同下完成 3 个目的地、至少 5 次演练；能复述"坐哪路、往哪开、哪站下"。
9. 无后台定位权限；隐私说明与实际行为一致。

## 8. 主要风险

| 风险 | 影响 | 缓解 |
|---|---|---|
| 百度路线接口权限/配额不满足 | 摘要无法上线 | M0 先确认 AK 服务、配额、SN；准备回退 URI。**实测个人认证只有 3 并发**，日配额尚未确认；客户端超时不释放服务端槽位，重试要限流 |
| 百度改了响应结构 | 摘要解析失败、白屏 | 解析层把结构异常作为可捕获结果返回（不是抛异常），走 §3.7 的"打开百度地图"回退；fixture 单元测试会在结构变化时立刻变红 |
| 摘要与百度地图方案不一致 | 老人按摘要坐错车 | 10 条线路对比；文案"以百度地图为准"；差异大时只对步行做直达导航 |
| 定位不准 | 步行距离/上车站错误 | 精度阈值提示；重试；回退百度地图 |
| 地点录入错误（同名/错入口） | 目的地错误 | 搜索 + 地图确认入口；保存 POI UID |
| A 方案代理不可用 | 摘要失败 | 3 秒超时 + 直接打开百度地图；监控与配额告警 |
| 百度地图未安装 | 无法导航 | 网页路线 + 安装指引 |
| 小屏/大字体溢出 | 首页滚动或按钮被遮 | 真机 1.3×/2× 测试；按钮最小高度 |
| 老人看不懂摘要 | 功能无效 | 纸面原型先验证；文案口语化；最多 6 行 |
| 百度数据条款/署名 | 合规风险 | 阅读并遵守百度地图开放平台条款；标注来源 |
| 范围蔓延（SOS/位置共享/AI） | 延期 | 本方案非目标清单；V2 另立 |

地点检索接口的实测注意事项（§4.6 的地点录入依赖它）：

- `/place/v3/search` 返回 **HTTP 404**，不可用；实测可用的是 `/place/v2/search`、`/place/v3/suggestion` 与 `/place/v3/detail`。
- `/place/v3/suggestion` 返回 15 位小数坐标，`/place/v2/search` 只返回 6 位。要精确坐标就用 suggestion 或 detail。
- v0.1 附录里"地点输入提示"的标题配的是"地点检索"的链接，是两个接口；本期两者都要用：输入提示给候选，地点详情给精确坐标与 UID。
- 坐标转换用 `/geoconv/v2/?model=`，实测语义：1 GCJ02→bd09ll、2 WGS84→bd09ll、3 bd09ll→bd09mc、4 bd09mc→bd09ll、5 bd09ll→GCJ02、6 用 bd09ll 输入时与 4 同输出。**model=5 就是 bd09ll→GCJ02**；不存在的是 **bd09ll→WGS84**（model ≥ 7 返回 `status=29 param error:model illegal`）。所以 §4.6"GPS 起点按需转换"只能正向转到 BD-09，不能把 BD-09 转回 GPS。
- **V1 客户端不调这个接口**：起点转换用 `coordtransform_dart` 的 `wgs84ToBd09` 本地完成，已与官方 model=2 在 15 个点上交叉验证（最大偏差 0.71 米），不需要 AK、不需要网络。官方接口只作校验基准。见 ADR 0001 事实 7 与 D3、`tools/coord-check/README.md`。
