# SeniorNav｜老年人出行导航与家属守护应用

**项目初步方案 v0.1**  
文档日期：2026-11-11　｜　阶段：方案评审 / 尚未启动开发  
开发目标：**先交付稳定的 Android V1，再开发 V2 家属守护；架构保留未来 iOS 扩展能力。**

> **一句话定位**：不重复开发地图和公交算法，复用成熟地图服务，为老人提供清晰、少操作的常用地点导航，并在第二阶段让家属能够远程配置与守护。

## 1. 项目背景与目标

### 1.1 使用场景

目标用户是一位日常主要**步行、乘公交或地铁**的安卓手机用户。现有地图产品虽有适老化模式，但“家、医院、菜市场、子女家”等常去地点未必能在简化界面便捷使用。家属希望先在手机上设置好地点，老人之后不必手动搜索；若后续有需要，家属还能远程查看位置、发出求助提醒。

### 1.2 核心原则

- **高频功能优先**：常用地点、一键回家、公交/步行两个出行方式位于首页；超出老人使用能力的设置隐藏到家属入口。
- **复用成熟能力**：地图、公交换乘方案、步行路径与导航语音由第三方地图客户端承担，不自行计算路线。
- **渐进交付**：V1 无后端、无需账号；V1 真机稳定后，V2 才引入账号、远程同步、定位服务和 SOS 通知。
- **隐私与可靠性优先**：定位共享须经本人或合法照护授权；设备离线、定位失败、地图未安装时均有可理解的提示。
- **一次开发，多端延展**：Flutter 共享 UI 和业务层；平台差异隔离在接口适配层。iOS 将来仍须 macOS + Xcode 进行编译和测试。

### 1.3 项目边界

本项目不是独立地图软件，也**不承诺**自动识别老人迷路、公交实时到站推送、自动开始全程语音导航、紧急救援保证到达。以上能力如有需求，应另立版本或专项验证。V2 不开发 AI 迷路识别和电子围栏自动报警，避免功能蔓延。

## 2. 版本范围与优先级

| 模块 | V1：极简导航 | V2：家属守护 | 不在当前范围 |
|---|---|---|---|
| 老人首页 | 大字体、大按钮、一键回家 | 保持兼容 | 复杂社交/内容功能 |
| 常用地点 | 本机添加/修改/删除，至少 5 个 | 家属远程新增、更新、同步 | 自动学习出行习惯 |
| 导航 | 公交/地铁与步行路线调起 | 沿用 V1 | 自研地图引擎、路径规划 |
| 联系家属 | 点击拨打预设号码（需电话确认） | SOS 附带位置、通知、拨号 | 替代 110/120 等救援 |
| 家属端 | 本机受保护的设置入口 | 手机网页/H5，设备配对 | 单独开发家属原生 App |
| 定位与轨迹 | 不做后台采集 | 家属查看最新位置和更新时间 | 全天候绝对实时保证 |
| 账号与后端 | 无 | 家属账号、配对权限、同步 API | 大型用户运营平台 |
| iOS | 保留架构适配接口 | 可在后续独立移植验收 | 本期 iOS 上线承诺 |

**版本冻结规则**：V1 未满足验收标准之前，不建立 V2 服务端业务代码；可以保留目录、接口和数据字段，但不提前实现远程功能。

## 3. V1 需求与交互

### 3.1 主要页面

**老人首页**：顶部展示“回家”大按钮；中部以卡片形式展示医院、菜市场、公园、子女家等常用地点；底部固定“步行 / 公交”切换和“联系家人”按钮。字大、对比明显，尽量避免多层菜单。

**家属设置页**：添加常用地点（名称、城市、详细地址、地图位置/POI、默认出行方式）、编辑排序、确认家庭地址、设置联系电话。入口可用长按或简单 PIN 防误触，但 V1 不将其视为互联网安全认证。

**导航调起页**：显示地点名、出行方式、即将打开的地图应用；若未安装百度地图，给出安装指引或可验证的网页回退方案；失败时返回首页，不出现空白页。

### 3.2 关键流程

```text
家属首次配置：
打开设置 → 搜索/录入常用地点 → 核对地图位置及入口 → 保存默认出行方式

老人日常使用：
打开 SeniorNav → 点击「回家」或某个地点 → 进入百度地图路线规划
                                           └→ 需要时切换「步行 / 公交」

遇到困难：
点击「联系家人」 → 跳转系统拨号界面 → 老人确认拨打
```

**地图边界**：百度地图 URI API 能调起路线规划，但不等于能保证“直接开始语音导航”或自动完成公交上下车提醒。V1 先实现可靠地调起正确路线；导航开始所需的后续点击动作，以真机测试结果为准。

### 3.3 地点输入设计

不能仅存“某某医院”之类模糊文字：同名地点可能导致导航错误。保存地点时建议同时记录**地点名称、城市、完整地址、经纬度、坐标系、可选 POI UID**，并由家属确认一次位置。

实现策略：先用 1～2 个已确认坐标的测试地点验证调起；进入 V1 可用版本时，优先复用百度地点输入提示/POI 检索服务完成家属搜索与选择。该服务需要单独申请密钥（AK）并核对额度、调用限制和安全配置，**与无需 AK 的百度 URI 调起接口不是同一项服务**。

## 4. 技术架构

### 4.1 V1：无后端

```text
                    SeniorNav（Flutter Android）
                                │
                  ┌─────────────┴────────────┐
                  │                          │
               UI/状态层                 业务服务层
           首页 / 地点 / 设置        Places / Navigation
                  │                          │
                  │             ┌────────────┴───────────┐
                  │             │                        │
                  └──────→ Drift/SQLite          Baidu URI Adapter
                       常用地点与偏好                 │
                                             已安装百度地图客户端
                                             公交/步行路线规划
```

### 4.2 V2：在 V1 基础上增加守护能力

```text
老人手机（Flutter）                      家属手机浏览器（H5）
  │                                                │
  ├─ 常用地点同步 ←──── HTTPS API / 身份绑定 ──────┤
  ├─ Traccar Client SDK ──位置上传──→ Traccar Server ─→ 位置展示
  └─ SOS 事件上报 ────────────────→ 轻量业务后端 ─→ 家属通知/确认
                 ↑                      │
                 └──────远程地点配置与授权管理────────┘
```

**架构约束**：Traccar 负责位置数据采集与跟踪；远程地点同步、老人—家属绑定、SOS 确认需要单独的业务逻辑。不能把“引入 Traccar SDK”理解为以上功能自然全部具备。建议先评估 Traccar Server 的账号和事件 API，再决定新增业务服务的最小边界。

### 4.3 目录建议

```text
seniornav/
├── app/                  # Flutter 应用：lib/features、core、data
│   ├── lib/features/     # home、places、navigation、settings、guardian(预留)
│   ├── lib/core/         # 主题、配置、异常处理、平台适配
│   └── lib/data/         # 本地存储、Repository；远程端口预留
├── backend/              # V2 再创建实际服务
├── guardian_web/         # V2 家属 H5
├── docs/                 # 本方案、ADR、测试记录
└── README.md
```

### 4.4 技术选型

| 层次 | 方案 | 选型理由 / 注意点 |
|---|---|---|
| 开发环境 | Ubuntu 22.04 + Android Studio / VS Code | 支持 Android 开发、真机调试；Linux 无需切换 Windows |
| 移动端 | Flutter + Dart | 业务逻辑和 UI 可复用于 iOS；当前只交付 Android |
| 状态管理 | Riverpod | 状态简洁、便于测试；避免过度抽象 |
| 本地存储 | Drift + SQLite | 常用地点持久化、迁移和跨平台支持 |
| 地图调起 | 百度地图 URI API + url_launcher | 复用路线规划；Android/iOS 分别封装调起逻辑 |
| 地点检索 | 百度 Place Suggestion / POI API（需验证） | 家属选点、获取唯一位置；可能需要 AK 与调用额度 |
| V2 定位 | 官方 traccar_client_sdk（候选） | Android/iOS 后台定位、离线缓存；需真机验证 |
| V2 后端 | Traccar Server + 最小业务 API | 位置查询尽量复用；地点同步和 SOS 自行实现 |
| V2 家属端 | 响应式 Web / H5 | 不额外开发第二个手机 App |

## 5. 数据结构与跨平台设计

### 5.1 常用地点（初稿）

| 字段 | 说明 |
|---|---|
| `id` | UUID；后续同步不依赖数据库自增 ID |
| `name` / `address` / `city` | 显示名称、完整地址、城市 |
| `latitude` / `longitude` / `coordSystem` | 坐标及坐标系（BD-09 / GCJ-02 / WGS84） |
| `poiUid` | 可选地图 POI 标识，帮助定位正确入口 |
| `defaultMode` | `walking` 或 `transit` |
| `isHome` / `sortOrder` | 是否家庭地址、首页显示顺序 |
| `updatedAt` / `deletedAt` | 预留 V2 同步、冲突和软删除 |

### 5.2 接口约束

- `PlaceRepository`：读写本地地点；V2 替换为本地优先 + 远程同步，UI 不感知来源。
- `NavigationLauncher`：接收地点与出行方式，负责 Android/iOS URI 差异、坐标转换和失败回退。
- `GuardianRepository`：V1 不实例化；V2 接管绑定、账户、同步和 SOS。
- `TrackingService`：仅 V2 引入；提供授权状态、最新上报时间及启停能力。

**关键提醒**：跨平台复用不等于无需 iOS 适配。百度地图 URL Scheme、系统拨号、定位授权、后台运行需要分别验证。iOS 编译和签名必须使用 macOS + Xcode。

## 6. V1 实施与验收

### 6.1 开发里程碑

| 里程碑 | 交付物 | 通过条件 |
|---|---|---|
| M0 技术探针 | 最小 Flutter Demo + 百度 URI 调起 | 安卓真机可进入正确地点的步行/公交路线；记录需点击几次 |
| M1 项目骨架 | 首页、主题、导航适配器、Repository | `flutter analyze`、基础测试通过 |
| M2 核心功能 | 常用地点管理、家/联系人、数据持久化 | 保存 5 个地点后重启仍完整 |
| M3 可靠性 | 异常处理、安装检测、真实出行测试 | 通过下方 V1 验收门槛，形成测试记录 |

**建议开发时先做 M0**。这是最大的不确定性：地图被调起后是否还需要老人自己选择路线、启动导航。若流程过于复杂，应在 M0 就评估百度 Android 地图 SDK 的“调起步行导航”能力或其他受支持的导航接口，而不是完成界面后再返工。

### 6.2 V1 验收标准

1. 家属能够录入并管理至少 **5 个常用地点**，其中包含唯一的“家”；地点信息经过位置核对。
2. 老人**无需输入文字**，可以从首页选择地点和默认出行方式；目标为最多 **2 次点击进入路线规划**，但不把它误写为“2 次点击开始全程语音导航”。
3. 公交/地铁与步行均能调出**正确目的地**的路线规划；真实测试包含不同地点及正常/无网/定位关闭等情况。
4. 关闭并重新打开 App 后，常用地点、排序及出行偏好仍然保留。
5. 百度地图未安装、URI 调起失败、地点数据不完整时有明确提示或回退，不出现无响应或误导性成功界面。
6. 字体与按钮在老人真实手机上可辨识；由实际使用者在陪同下完成至少 **3 次完整出行场景演练**。
7. 编写测试记录，确认坐标系无偏移，家庭地址和医院等重要地点入口正确。

**进入 V2 的门槛**：V1 连续日常试用约 1 周，未发现阻断老人出行的重大缺陷；否则继续修复，不提前开工 V2。

## 7. V2 需求、隐私与验收

### 7.1 功能分解

| 子功能 | 最小实现 | 验收关注点 |
|---|---|---|
| 家属绑定 | 老人端授权 + 一次性配对码/二维码 | 过期、撤销、错误配对不可获得位置 |
| 远程地点管理 | 家属 H5 增删改常用地点，老人端同步 | 同步成功/失败显示，离线保留原数据 |
| 位置共享 | 用户明确同意后上传 GPS，家属查看位置 | 显示时间戳、精度及“位置可能已过期” |
| 位置可靠性 | Traccar SDK 缓存、恢复上传 | 断网、锁屏、省电模式下按设备实测记录 |
| SOS 求助 | 老人点击后提供拨号与位置求助上报 | 家属收到可见通知并可确认；失败时显式提示 |
| 退出与撤权 | 老人端关闭共享，家属端解除绑定 | 停止新数据共享、权限即时失效 |

### 7.2 V2 隐私与安全底线

- 对位置共享、持续后台定位取得清晰、独立、可撤销的授权；老人能够看到“共享中”状态。
- 家属位置查看必须登录，设备与家属账户经过授权配对；服务端逐次校验设备访问权，不能使用公开无鉴权位置链接。
- 网络传输使用 HTTPS；令牌存安全存储；不将密钥、家庭地址、位置明文写入公共日志或 Git 仓库。
- 设置最小化数据保留策略，初始建议仅保存必要的近期轨迹（如 7 天，家属可选择更短）；支持主动删除。
- **SOS 不替代直接拨打电话**。网络失败时仍可打开系统拨号；只有服务端确认接收才提示“求助已发送”。
- 在家属页面明确展示最后一次定位时间、精度和设备在线状态，避免把历史位置误认为实时位置。

### 7.3 V2 验收标准

1. 家属通过有效授权配对后，可以远程编辑常用地点；老人端重新联网能够同步成功。
2. 家属页面显示最新定位及其**时间、精度、在线状态**；超过设定时限自动标记“位置已过期”。
3. 断网恢复后继续位置上传；安卓锁屏、系统省电等工况形成实测结果，不宣称绝对实时。
4. SOS 至少提供**拨号通道**及**联网求助通道**；未成功发送时明确显示失败，并保留电话求助。
5. 撤销家属授权后，旧账户不能继续访问位置或修改地点。
6. Android V2 经日常场景试用，且不降低 V1 导航操作的易用性与稳定性。

## 8. 主要风险和决策点

| 风险 | 影响 | 缓解方式 / 触发决策 |
|---|---|---|
| URI 仅到路线规划页 | 老人仍需多次操作 | **M0 先测试**；必要时评估官方原生导航调起 SDK |
| 同名地点、坐标混用 | 错误目的地，具有安全风险 | 详细地址 + POI/坐标确认；统一保存坐标系并真机校验 |
| 地图客户端升级 | URI 调起行为变化 | 记录兼容版本、降级处理、回归测试 |
| 安卓后台定位受限制 | 家属看到位置延迟 | 使用官方定位方案、明确更新时间和电池策略 |
| SOS 推送不可靠 | 求助事件未及时收到 | 电话作为独立兜底，服务端确认与状态反馈 |
| 家属配置同步冲突 | 目的地被错误覆盖 | 版本号、更新时间、操作回执；优先提示冲突 |
| iOS 平台适配差异 | 未来移植返工 | 隔离导航与定位适配层；后期在 Mac + 真机验证 |
| 第三方服务条款/额度 | 调用限制和运营成本 | V1 核验百度使用条款；V2 上线前核查部署成本与许可 |

## 9. 工作量、阶段与资源

**粗略工作量（个人开发、使用 Codex/Claude Code 辅助）**：M0 半天～2 天；V1 可用版约 1～2 周；稳定性验证还需真实试用时间；V2 约 2～4 周起，取决于 Android 后台定位、服务器部署、家属配对、通知链路的实际调试情况。以上是计划尺度，不是交付保证。

**硬件/软件**：Ubuntu 22.04 开发电脑；Android Studio 或 VS Code；Flutter SDK；老人真实安卓手机；可用于验证定位和地图的网络环境。V2 再决定服务器/域名/HTTPS、通知通道及日常维护费用。

**iOS 策略**：保持数据模型与服务端 API 平台无关，但本期不承担 iOS 签名、审核与后台定位测试成本。未来扩展时以 Mac + iPhone 做独立验收。

## 10. 开工前决策与第一阶段任务

**当前已确定**：先 V1 后 V2；安卓真机优先；Linux 开发；Flutter；优先复用百度地图；V2 优先评估 Traccar；不开发 AI 迷路识别。

**尚待技术验证**：目标手机型号/Android 版本；百度地图是否已安装；URI 在“步行/公交”流程中的实际点击数；地点选择 API 的密钥与调用方式；真实地址的坐标准确性；V2 服务器部署与通知方式。

**第一项开发任务（M0）**：新建 Flutter Demo，首页仅放“回家-步行”“回家-公交”两个测试按钮，以一个已核对的测试坐标调起百度地图；在真实安卓手机上录屏并记录每一步。**M0 通过后，再做完整 V1 UI 和数据库。**
