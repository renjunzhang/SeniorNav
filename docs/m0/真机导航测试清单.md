**状态：已开始真机验证（2026-11-13），M0 未全部验收；初版暂选 SDK，D1 的完整验收保持开放。**

## 1. 测什么、用哪个包

|---|---|---|---|
| 主 App 探针 `app-debug.apk` | `bash tools/build_probe.sh`（注入真实坐标） | M0-2/3/4：URI 调起、点击次数、语音导航 | 与 SDK 探针**同包名，只能装一个** |

入口精度测试须用已核验地点注入包；URI 行为也可用公共地标对照（默认包目的地是虚构示例点），但**不要外发、不要上传网盘、不要贴 issue**。
截图与录屏入库前按 `docs/GIT_COMMIT_RULES.md` §3.7 脱敏：删设备序列号、手机号、精确家庭位置，

### 2.0 本次设备与测试方法（2026-11-13）

- 上述设备与版本已由接手者重新读取；21.15.0 满足步行调起 ≥ 8.8 的门槛。
- 测试前关闭自动旋转并固定竖屏：`adb shell settings put system accelerometer_rotation 0`、
  `adb shell settings put system user_rotation 0`。横竖坐标混用会导致点击落空。
- 前一位执行者记录每次 App 调起均出现 Flyme 确认框；接手时 A～G 等热启动未再次弹框。
  因此只能记录各次实际成本，**不能推断所有设备或每次调用都必弹**。
- 接手时发现百度可进入 `flyme-mini-window`。此时 UI dump 可能仍反映之前页面或报
  `could not get idle state`；步行导航须核对实际画面，不能只凭 `launchUrl=true`。
- 语音本轮不作为继续测试的前置条件（用户明确暂不关注），仍记「未确认」。

### 2.1 百度地图版本门槛：先验版本，再测步行

**版本号不是背景信息，是 §6 全部步行条目的前置条件。** 插件源码
`bmf_open_navi_options.dart:9-22` 的版本注释写明（ADR 0004 事实 6）：

| 客户端版本 | 能力 | 对本次测试的影响 |
|---|---|---|
| ≥ 8.8 | 支持 `WalkNavi` | §6 的 H/I/J/K/L 才是有效测试 |
| 8.6.9 ～ 8.8 | 有步行导航，但无 `WalkNavi` 调起 | `walknavi` 可能落到预览页，**别误判成参数写错** |
| < 8.6.9 | **不支持步行导航** | §6 全部条目无效，必须先升级客户端再测 |

所以顺序是：**先跑上面的 `versionName` 命令记下版本 → 若 < 8.8，先去商店升级 → 再测 §6**。
否则会把「客户端太旧」记成「URI 参数不对」，得出错误的 D1 依据。
老人手机上的百度地图很可能长期不更新，这正是方案 §3.7 新增「版本过旧」降级行的原因；
**旧版本上 `walknavi` 的具体失败形态（报错 / 静默回首页 / 落预览页）本身就是要采集的数据**，
升级前顺手记一次，比升级后补测更真实。

## 3. 点击次数怎么数

统一口径，否则各条没法比：

- 从 **SeniorNav 首页那一次点击记为 1**，数到目标界面出现为止的全部触屏点击，
  **包含百度地图内部的**方案选择、弹窗「同意/允许」、「开始导航」等。
- 系统权限弹窗里的「允许」也计 1 次，并单独记下来（首次安装才有，属于一次性成本）。
- 目标界面定义：公交 = 看得见「坐哪路、往哪开、哪站下」的线路详情；
  步行 = 进入导航态（有方向指引/语音），不是路线预览页。
- 每条同时记：**落地界面**（首页 / 路线列表 / 线路详情 / 导航态 / 报错）、**耗时**、
  **是否自动播报**、**目的地是否正确**。

判定参考：方案 §1.3 要「先摘要后导航」，§6.2 第 5 条要「步行优先直接进步行导航」。
公交理想是 1 次直达线路详情；若必须 2 次（调起 + 选方案），摘要页就要替老人把方案选好，
这正是 §4.4 只选 1 条推荐方案的理由。**阈值不是硬指标，实测数字回填后再定。**

### 4.1 接手回退实测（2026-11-13）

- 模拟未安装：公交与步行均进入系统浏览器的百度路线相关页面，出现「我的位置」起点与地点候选；
  **未直接展示路线**。期间出现 Flyme 打开确认及权限相关弹窗，其完整处理链未量清，不能声称已完成回退验收。
- 可恢复的真实不可用对照：`pm disable-user --user 0 com.baidu.BaiduMap` 后重启探针，
  页面实际显示 `canLaunchUrl=false`；公交按钮进入浏览器。测试后已 `pm enable` 恢复百度。
- 禁用对照不等于卸载；**真卸载仍未测**，本次未清除百度应用数据。
- 原生 App 中 `origin=我的位置` 可用，不代表浏览器会自动定位；网页需要单独解决起点定位/选择链。

**计数补充**：下表 A～G 的「1」只表示接手复测从探针按钮到落地页的一次点击，
不包含测试准备时滚动探针找按钮。公交未进入详情，不能写成「1 次完成导航」。
前次交接中的 O1「3 次」也不含权限授予后的完整重入流程，不能当成端到端总数。

## 5. M0-2 公交：哪种参数组合点击最少

探针页「M0-2」区的按钮标签与下表一一对应，不用另写代码。

| 标签 | 变量 | 要回答的问题 | 实测点击数 | 落地界面 |
|---|---|---|---|---|
| A | 仅名称，无 uid 无坐标 | 名称能不能直接规划 | 1 | 路线列表；名称可规划，入口精度未核验 |
| B | 父 POI uid + navi_location | uid 是否让终点落到出入口 | 1 | 路线列表；父 POI 名称正确，入口精度未核验 |
| C | B + `index=0&target=1` | **能否一次直达线路详情** | 1 | 路线列表；index/target 未直达详情 |
| D | C + `sy=3`（少步行） | 策略是否影响落地页 | 1 | 路线列表；策略改变路线，未改变落地层级 |
| D' | C + `sy=0`（推荐） | 与 D 对比，D2 已定默认用 0 | 1 | 路线列表；未直达详情 |
| E | `src=webapp.seniornav.mobile` | 文档规则与官方示例前缀不一致，哪个被接受 | 1 | 路线列表；webapp 前缀被接受 |
| F | 终点用门的子 POI | 父 uid 是否已足够 | 1 | 路线列表；终点显示注入的门名称，落点精度未核验 |
| G | 名称含竖线、冒号、斜杠 | `name:…\|latlng:…` 会不会被解析错 | 1 | 无公交方案页；终点变成「我的位置」，提示距离太近 |

**origin 三种写法**（决定 V1 要不要申请定位权限，方案 §4.7）：

| 标签 | 写法 | 要回答的问题 | 百度取的起点 | 是否正确 |
|---|---|---|---|---|
| O1 | 省略 `origin` | 文档标必选，省略是否仍自动定位 | 我的位置 | 前次交接：可规划；首次位置授权后退回探针，第二次调起成功 |
| O2 | `origin=我的位置` | 字面量是否被识别为当前位置 | 我的位置 | 接手公共地标对照成功，落到路线列表 |
| O3 | 显式经纬度 | 对照组，确认参数被接受 | 显式起点被接受（与 O2 路线不同） | 接手公共地标对照能规划；起点落点精度尚未核验 |

接手 O2/O3 用 adb 串行发送 URI，终点固定「合肥火车站」，O3 起点取公共地标 fixture；
两次均有路线列表，O3 首条约 25 分钟 / 10 站。**adb 对照不计作 SeniorNav 点击次数验收**。
O1 授权时选「仅本次允许」后返回探针，第二次调起才正常落地；首次授权成本不能只记一个弹窗。
G 使用的是不存在的虚构名称，因此只证明本次未正确落地，尚不能归因于竖线/冒号解析。

O1/O2 只要有一个能拿到手机当前位置，V1 就可以不申请定位权限；
两个都不行则必须前台定位一次（§4.7 的口径）。
**注意 O3 借用小区另一个门的坐标冒充当前位置，只为验证参数，不代表真实起点。**

## 6. M0-3 步行：能否直接开始语音导航

**前置：先按 §2.1 确认百度地图 ≥ 8.8 并记下版本号，否则本表结论无效。**

| 标签 | 变量 | 要回答的问题 | 是否进导航态 | 是否自动播报 | 点击数 |
|---|---|---|---|---|---|
| H | `walknavi` 不带 mode（照官方示例） | 示例写法是否够用 | 是（冷启动复核，小窗） | 未确认 | 1；首次热启动停留旧页，另记异常 |
| I | `walknavi` 带 `mode=walking` | 文档标必选、示例未给，哪个对 | 是（小窗） | 未确认 | 1 |
| J | 省略 `origin` | 百度是否自动取当前位置 | 是（小窗） | 未确认 | 1 |
| K | 终点用 POI 几何中心 | **对照：终点是否偏离主要出入口** | 是；入口偏移未量出 | 未确认 | 1 |
| L | 同坐标但 `coord_type=wgs84` | 故意错配，量坐标系混用的偏移 | 是；路线总长改变，落点偏移未量出 | 未确认 | 1 |
| M | `direction?mode=walking` | 对照组，预期只到路线预览页 | 否；预览页有「开始导航」 | 未确认 | 1 到预览页 |

接手 H/I/J/K 的导航底栏约 11.7 公里 / 2 小时 57 分钟，L 约 12.2 公里 / 3 小时 3 分钟。
这是当前真机状态下的**路线总长**，差值约 0.5 公里不能当作终点坐标偏移；
也不能用该长路线推断显式 origin 被严格采用。H 热启动曾停留旧页，冷启动后复核导航态；
I～M 各项前终止百度进程以隔离上一轮导航。K/L 的入口偏移米数仍待实测，不关闭精度验收。

K 决定数据模型存 `navi_location` 还是 `location`；L 量出的偏移就是评审 P0-3「坐标混用」的代价，
也是 ADR 0001 统一 BD-09 的实证。**这两条即使结论是「没问题」也要记数字**，
否则将来换数据源时没有基线。

## 7. 百度地图关怀版是否支持 URI 调起

### 7.1 本机静态调研（已完成，2026-11-12）

| 项 | 结论 | 依据 |
|---|---|---|
| 关怀版是不是独立 App | **是**，包名 `com.baidu.maps.caring` | 小米应用商店详情页（开发者：北京百度网讯科技有限公司，v1.1.5） |
| 与「百度关怀版」是否同一个 | **不是**，后者包名 `com.baidu.searchbox.senior`，是百度 App 的长辈版 | 第三方下载站信息，需真机复核 |
| 与正式版关系 | 正式版是 `com.baidu.BaiduMap`，两者可共存 | 主 App manifest 的 `<queries>` 已声明该包名 |
| 是否支持 `baidumap://` | **未知，没有任何公开文档说明** | 官方 URI 文档只写「百度地图」，未区分版本 |
| 是否支持 `walknavi` / `index` / `target` | **未知** | 同上 |

第三方站点列的厂商名不一致（「北京百度网讯科技有限公司」与「北京百度在线网络技术（北京）有限公司」），
版本号也从 1.0.5 到 1.1.8 不等，**这些站点不是权威来源，只用来确认包名存在**。
真机上以 `dumpsys package` 的签名与版本为准。也不要从第三方站下载 APK 装机，走手机自带商店。

### 7.2 真机三步（不需要改 App 代码）

`url_launcher` 不能指定目标包名，所以用 adb 强制包名，这比改代码更能给出确定结论。

**第一步：确认装了哪个、版本与签名**

```bash
adb shell pm list packages | grep -i baidu
adb shell dumpsys package com.baidu.maps.caring > /tmp/caring.txt
```

在 `/tmp/caring.txt` 里找 `versionName` 与 `Signer`/`certificates`，与正式版对比是否同一张证书。

**第二步：看它有没有注册 `baidumap` scheme**

```bash
grep -n -A6 'android.intent.action.VIEW' /tmp/caring.txt | grep -i -B2 -A4 'baidumap\|Scheme'
adb shell pm resolve-activity --brief -a android.intent.action.VIEW -d 'baidumap://map/direction'
```

`resolve-activity` 给出系统默认会调起谁。若关怀版注册了同一 scheme，
装了两者时系统可能弹选择框——**这本身就是点击次数 +1，要记下来**。

**第三步：强制用关怀版打开，看落地界面**

```bash
adb shell "am start -a android.intent.action.VIEW -d 'baidumap://map/direction?destination=合肥火车站&mode=transit&coord_type=bd09ll&src=andr.seniornav.mobile' -p com.baidu.maps.caring"
adb shell "am start -a android.intent.action.VIEW -d 'baidumap://map/walknavi?destination=31.891171,117.323703&coord_type=bd09ll&src=andr.seniornav.mobile' -p com.baidu.maps.caring"
```

外层双引号给本机 shell、内层单引号给设备 shell，`&` 才不会被打断。
上面用的是**公共地标坐标**（取自 `app/test/fixtures/`），不含私人位置；
要测真实住址就在手机本地改，命令与结果都不入库。

### 7.3 判定表

| 观察到的现象 | 结论 | 对 V1 的影响 |
|---|---|---|
| `Error: Activity not started, unable to resolve Intent` | 关怀版**不支持**该 URI | 只能调正式版；关怀版作为「老人自己手动用」的备选写进说明 |
| 打开了但停在首页/搜索页 | 支持 scheme，**不支持这些参数** | 记录哪些参数被忽略；点击次数会上升 |
| 直接到线路详情 / 导航态 | **支持** | 可考虑优先调关怀版（大字更适老），但要记是否弹选择框 |
| 弹「选择打开方式」 | 两者都注册了 scheme | 需用 `Intent.setPackage` 固定目标，那要加一个平台通道（**先别做，等结论**） |

主 App manifest 的 `<queries>` 里已有 scheme 级 `<intent>` 声明，
所以**关怀版若注册了 `baidumap`，包可见性不需要再改**；`canLaunchUrl` 也会因此变 true，
但它分不清是正式版还是关怀版——这一点在只装了关怀版的手机上要单独验一次。

## 8. SDK 探针（M0 任务 2 的运行时部分）

步骤见 `tools/sdk-probe/README.md`，此处不重复。要点：

- 首轮六项均 `发起=false / PERMISSION_UNFINISHED`；修正后在用户授权继续开发时完成新一轮六次串行调用，5 项正常路线 + 1 项短途公交无结果，见 ADR 0003 §8 与 ADR 0006。
- 需要**另一个 AK**：Android SDK 类型，绑包名 `com.seniornav.seniornav` + 调试签名 SHA1
  `CD:11:33:84:63:A3:60:58:9E:9A:B6:46:8E:8D:8B:87:40:E6:B6:00`。服务端 AK 不能用。
- 跑的是与 fixtures 相同的**三条 OD × 公交/步行 = 6 次串行请求**，其中 95 米那条专门测
  SDK 怎么表达「没有公交方案」（Web API 侧是 `status==0` 且 `routes` 为空）。
- 探针把 SDK getter 序列化成 Web API 的 JSON 形状并保留分组，落盘后用
  `app/tool/parse_sdk_dump.dart` 走**现有解析器与文案规则**判定字段够不够，不另写映射。
- 交回物：六个 dump + `adb logcat -s SDKPROBE` 片段（含每条 OD 的延迟与缺失字段计数）。

## 12. 百度地图 22.2.0 跳转复测（2026-11-14，P1-跳转）

百度地图已由 21.15.0 升级到 **22.2.0**，§5/§6 的旧实测不再直接适用，本轮用 adb 串行重发
5 条 URI（公共地标「合肥火车站」31.891171,117.323703，`origin=我的位置`，无 uid，
编码与 App 的 `Uri.replace(queryParameters:)` 一致；每条前 force-stop 百度隔离上一轮）。
截图与 UI dump 查看后已删除，未入库。

| 探针 | URI 变量 | 落地界面 | 是否直达详情/导航 |
|---|---|---|---|
| P1 | `mode=transit&sy=4`（App 公交现状） | 公共交通路线列表，「推荐路线」tab，结果均为纯公交 | 否 |
| P2 | P1 + `index=0&target=1` | 同 P1 列表 | **否，index/target 仍被忽略** |
| P3 | `mode=transit&sy=6`（App 地铁现状） | 列表，「推荐路线」tab，结果均含地铁段 | 否 |
| P4 | P3 + `index=0&target=1` | 同 P3 列表 | **否** |
| P5 | `walknavi` 省略 origin（App 步行现状） | **直接进入步行导航态**（方向指引+已用时计时） | 是，1 次调起 |

结论与决定：

- **没有找到更少点击的参数组合，跳转代码不改。** 公交/地铁仍落路线列表，老人需再点 1 次
  选方案；`index=0&target=1` 在 22.2.0 依旧无效。步行已是 1 次调起进导航态，维持现状。
- sy=4/sy=6 仍影响**结果内容**（纯公交 vs 含地铁），但都不切换 tab（界面均显示「推荐路线」）。
  现有 sy 映射继续有效。
- 22.2.0 新现象：列表首卡是**打车广告**（「打车21分钟 节约38分钟」），URI 无法去除；
  步行导航态底部有可关闭的音乐推广 banner。老人可能误点广告，试用说明需提醒「点公交/地铁
  线路卡片，不要点打车卡片」。
- 本轮在凌晨查询，列表给每条路线标了「不在运营时间内」红色提示（客户端展示层校验，
  与 ADR 0002 A7「SDK 不校验运营时间」不矛盾，客户端摘要仍须自行比对首末班）。
- P5 路线总长 15.7 公里/约 4 小时，是手机真实位置到公共地标的距离，只证明导航态进入，
  不代表入口精度；播报仍未确认。
- **未复测**：带 `destination_uid` 的调起（无公共 uid 可用，21.15.0 的 B/F 结论静态沿用，
  待真机 App 内点「打开地图导航」时观察确认）、Flyme 确认框（本轮 adb 直发未出现）、
  网页回退链。
