## 3. 点击次数怎么数

统一口径，否则各条没法比：

- 从 **SeniorNav 首页那一次点击记为 1**，数到目标界面出现为止的全部触屏点击，
  **包含百度地图内部的**方案选择、弹窗「同意/允许」、「开始导航」等。
- 系统权限弹窗里的「允许」也计 1 次，并单独记下来（首次安装才有，属于一次性成本）。
- 目标界面定义：公交 = 看得见「坐哪路、往哪开、哪站下」的线路详情；
  步行 = 进入导航态（有方向指引/语音），不是路线预览页。
- 每条同时记：**落地界面**（首页 / 路线列表 / 线路详情 / 导航态 / 报错）、**耗时**、
  **是否自动播报**、**目的地是否正确**。

判定参考：方案 §1.3 要「先摘要后导航」，§6.2 第 5 条要「步行优先直接进步行导航」。
公交理想是 1 次直达线路详情；若必须 2 次（调起 + 选方案），摘要页就要替老人把方案选好，
这正是 §4.4 只选 1 条推荐方案的理由。**阈值不是硬指标，实测数字回填后再定。**

## 5. M0-2 公交：哪种参数组合点击最少

探针页「M0-2」区的按钮标签与下表一一对应，不用另写代码。

| 标签 | 变量 | 要回答的问题 | 实测点击数 | 落地界面 |
|---|---|---|---|---|

| B | 父 POI uid + navi_location | uid 是否让终点落到出入口 | | |
| C | B + `index=0&target=1` | **能否一次直达线路详情** | | |

| D' | C + `sy=0`（推荐） | 与 D 对比，D2 已定默认用 0 | | |
| E | `src=webapp.seniornav.mobile` | 文档规则与官方示例前缀不一致，哪个被接受 | | |
| F | 终点用门的子 POI | 父 uid 是否已足够 | | |
| G | 名称含竖线、冒号、斜杠 | `name:…\|latlng:…` 会不会被解析错 | | |

**origin 三种写法**（决定 V1 要不要申请定位权限，方案 §4.7）：

| 标签 | 写法 | 要回答的问题 | 百度取的起点 | 是否正确 |
|---|---|---|---|---|
| O1 | 省略 `origin` | 文档标必选，省略是否仍自动定位 | | |
| O2 | `origin=我的位置` | 字面量是否被识别为当前位置 | | |
| O3 | 显式经纬度 | 对照组，确认参数被接受 | | |

O1/O2 只要有一个能拿到手机当前位置，V1 就可以不申请定位权限；
两个都不行则必须前台定位一次（§4.7 的口径）。
**注意 O3 借用小区另一个门的坐标冒充当前位置，只为验证参数，不代表真实起点。**

## 7. 百度地图关怀版是否支持 URI 调起

### 7.1 本机静态调研（已完成，2026-11-12）

| 项 | 结论 | 依据 |
|---|---|---|
| 关怀版是不是独立 App | **是**，包名 `com.baidu.maps.caring` | 小米应用商店详情页（开发者：北京百度网讯科技有限公司，v1.1.5） |
| 与「百度关怀版」是否同一个 | **不是**，后者包名 `com.baidu.searchbox.senior`，是百度 App 的长辈版 | 第三方下载站信息，需真机复核 |
| 与正式版关系 | 正式版是 `com.baidu.BaiduMap`，两者可共存 | 主 App manifest 的 `<queries>` 已声明该包名 |
| 是否支持 `baidumap://` | **未知，没有任何公开文档说明** | 官方 URI 文档只写「百度地图」，未区分版本 |
| 是否支持 `walknavi` / `index` / `target` | **未知** | 同上 |

第三方站点列的厂商名不一致（「北京百度网讯科技有限公司」与「北京百度在线网络技术（北京）有限公司」），
版本号也从 1.0.5 到 1.1.8 不等，**这些站点不是权威来源，只用来确认包名存在**。
真机上以 `dumpsys package` 的签名与版本为准。也不要从第三方站下载 APK 装机，走手机自带商店。

### 7.2 真机三步（不需要改 App 代码）

`url_launcher` 不能指定目标包名，所以用 adb 强制包名，这比改代码更能给出确定结论。

**第一步：确认装了哪个、版本与签名**

```bash
adb shell pm list packages | grep -i baidu
adb shell dumpsys package com.baidu.maps.caring > /tmp/caring.txt
```

在 `/tmp/caring.txt` 里找 `versionName` 与 `Signer`/`certificates`，与正式版对比是否同一张证书。

**第二步：看它有没有注册 `baidumap` scheme**

```bash
grep -n -A6 'android.intent.action.VIEW' /tmp/caring.txt | grep -i -B2 -A4 'baidumap\|Scheme'
adb shell pm resolve-activity --brief -a android.intent.action.VIEW -d 'baidumap://map/direction'
```

`resolve-activity` 给出系统默认会调起谁。若关怀版注册了同一 scheme，
装了两者时系统可能弹选择框——**这本身就是点击次数 +1，要记下来**。

**第三步：强制用关怀版打开，看落地界面**

```bash
adb shell "am start -a android.intent.action.VIEW -d 'baidumap://map/direction?destination=合肥火车站&mode=transit&coord_type=bd09ll&src=andr.seniornav.mobile' -p com.baidu.maps.caring"
adb shell "am start -a android.intent.action.VIEW -d 'baidumap://map/walknavi?destination=31.891171,117.323703&coord_type=bd09ll&src=andr.seniornav.mobile' -p com.baidu.maps.caring"
```

外层双引号给本机 shell、内层单引号给设备 shell，`&` 才不会被打断。
上面用的是**公共地标坐标**（取自 `app/test/fixtures/`），不含私人位置；
要测真实住址就在手机本地改，命令与结果都不入库。

### 7.3 判定表

| 观察到的现象 | 结论 | 对 V1 的影响 |
|---|---|---|
| `Error: Activity not started, unable to resolve Intent` | 关怀版**不支持**该 URI | 只能调正式版；关怀版作为「老人自己手动用」的备选写进说明 |
| 打开了但停在首页/搜索页 | 支持 scheme，**不支持这些参数** | 记录哪些参数被忽略；点击次数会上升 |
| 直接到线路详情 / 导航态 | **支持** | 可考虑优先调关怀版（大字更适老），但要记是否弹选择框 |
| 弹「选择打开方式」 | 两者都注册了 scheme | 需用 `Intent.setPackage` 固定目标，那要加一个平台通道（**先别做，等结论**） |

主 App manifest 的 `<queries>` 里已有 scheme 级 `<intent>` 声明，
所以**关怀版若注册了 `baidumap`，包可见性不需要再改**；`canLaunchUrl` 也会因此变 true，
但它分不清是正式版还是关怀版——这一点在只装了关怀版的手机上要单独验一次。

## 8. SDK 探针（M0 任务 2 的运行时部分）

步骤见 `tools/sdk-probe/README.md`，此处不重复。要点：

- 编译已在开发机验证通过，**检索调用、字段完整性、延迟全部待真机**。
- 需要**另一个 AK**：Android SDK 类型，绑包名 `com.seniornav.seniornav` + 调试签名 SHA1
  `CD:11:33:84:63:A3:60:58:9E:9A:B6:46:8E:8D:8B:87:40:E6:B6:00`。服务端 AK 不能用。
- 跑的是与 fixtures 相同的**三条 OD × 公交/步行 = 6 次串行请求**，其中 95 米那条专门测
  SDK 怎么表达「没有公交方案」（Web API 侧是 `status==0` 且 `routes` 为空）。
- 探针把 SDK getter 序列化成 Web API 的 JSON 形状并保留分组，落盘后用
  `app/tool/parse_sdk_dump.dart` 走**现有解析器与文案规则**判定字段够不够，不另写映射。
- 交回物：六个 dump + `adb logcat -s SDKPROBE` 片段（含每条 OD 的延迟与缺失字段计数）。
